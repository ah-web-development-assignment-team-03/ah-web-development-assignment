# 동시성 문제 해결을 위한 Event-Driven Architecture 설계

## 1. 설계 배경

현재 폐렴 예측 요청은 FastAPI 프로세스가 AI 모델을 직접 실행한 뒤 결과를 저장한다. 이 방식은 다음 문제가 있다.

- CPU 중심의 추론이 API 처리 시간과 워커 스레드를 오래 점유한다.
- 동일 진료기록에 요청이 동시에 들어오면 여러 요청이 같은 추론을 중복 수행한다.
- 결과의 유일성 제약으로 중복 저장은 막을 수 있지만, 이미 사용한 추론 자원은 회수할 수 없다.
- API 프로세스가 종료되면 진행 중인 작업과 재시도 정보가 사라진다.
- API 서버와 AI 추론 서버의 확장 단위를 분리할 수 없다.

따라서 요청 처리와 AI 추론을 이벤트로 분리하고, Redis가 작업 대기열을 관리하도록 설계한다.

## 2. 기술 선택

작업 대기열은 Redis Streams와 Consumer Group을 사용한다.

| 항목 | 적용 방식 |
|---|---|
| 작업 저장 | Redis Stream에 예측 작업 이벤트 추가 |
| 작업 분배 | Consumer Group이 한 작업을 한 AI 워커에 전달 |
| 처리 확인 | 결과 저장이 끝난 뒤 `XACK` 수행 |
| 장애 복구 | 장시간 미완료된 Pending 작업을 `XAUTOCLAIM`으로 회수 |
| 재시도 | 재시도 횟수와 오류 정보를 이벤트에 기록 |
| 실패 격리 | 허용 횟수를 넘긴 작업은 Dead Letter Stream으로 이동 |
| 중복 방지 | `record_id`와 `ai_model` 조합을 멱등성 키로 사용 |

FastAPI의 `BackgroundTasks`나 `asyncio.create_task`는 API 프로세스가 종료되면 작업이 유실될 수 있고 추론 자원을 API와 분리하지 못하므로 사용하지 않는다. Celery도 Redis 기반 작업 분리에 적합하지만, 이번 설계는 작업 상태와 Pending 복구 과정을 직접 제어하기 위해 Redis Streams를 사용한다.

### 구성 요소별 책임

**FastAPI**

- 인증·인가, 진료기록과 X-ray 존재 여부를 검증한다.
- 기존 완료 결과 또는 진행 중인 작업을 확인한다.
- 신규 작업 상태를 DB에 `PENDING`으로 기록하고 Redis Stream에 이벤트를 발행한다.
- 추론을 직접 실행하지 않고 `202 Accepted`와 작업 식별자를 반환한다.
- 작업 상태 및 완료 결과 조회 API를 제공한다.

**Redis**

- `prediction:tasks` Stream에서 작업을 대기시킨다.
- Consumer Group을 통해 여러 AI 워커에 작업을 분배한다.
- 처리 중인 작업을 Pending Entries List로 관리한다.
- 복구 대상 작업과 최종 실패 작업을 관리한다.

**AI Worker**

- Consumer Group에서 작업을 가져온다.
- X-ray 이미지를 읽고 폐렴 예측 모델을 실행한다.
- 결과와 작업 상태를 MySQL에 저장한다.
- DB 저장 성공 후에만 작업을 승인한다.
- 일시적 오류는 재시도하고 영구 오류는 실패 상태와 원인을 기록한다.

**MySQL**

- 작업 상태와 최종 예측 결과의 기준 저장소 역할을 한다.
- `(record_id, ai_model)` 유일성 제약으로 최종 결과의 중복 저장을 차단한다.

## 4. 처리 흐름

1. 클라이언트가 진료기록의 폐렴 예측을 요청한다.
2. FastAPI가 요청 권한, 진료기록, X-ray 이미지와 기존 결과를 확인한다.
3. 완료 결과가 있으면 해당 결과를 즉시 반환한다.
4. 진행 중인 동일 작업이 있으면 기존 작업 식별자와 상태를 반환한다.
5. 신규 작업이면 MySQL에 `PENDING` 상태를 기록하고 Redis Stream에 작업 이벤트를 발행한다.
6. AI 워커가 Consumer Group을 통해 작업을 가져와 상태를 `PROCESSING`으로 변경한다.
7. AI 워커가 모델 추론을 수행하고 결과를 MySQL에 저장한다.
8. 저장에 성공하면 상태를 `SUCCEEDED`로 변경하고 Redis에 `XACK`을 보낸다.
9. 클라이언트는 작업 조회 API를 통해 상태와 완료 결과를 확인한다.

## 5. 동시성 및 정합성 제어

### 동일 작업의 중복 요청

`record_id`와 `ai_model` 조합을 멱등성 키로 사용한다. FastAPI는 같은 키의 `PENDING`, `PROCESSING`, `SUCCEEDED` 작업이 있으면 새 이벤트를 만들지 않는다. 동시에 요청이 통과하는 상황은 DB 유일성 제약으로 최종 방어한다.

### 메시지 중복 전달

Redis Streams는 장애 상황에서 같은 메시지가 다시 전달될 수 있으므로 AI 워커는 멱등하게 동작해야 한다. 워커는 추론 전에 완료 결과를 확인하고, 결과 저장 시에도 동일한 유일성 제약을 사용한다. 이미 완료된 작업은 추론 없이 승인한다.

### DB 저장과 메시지 발행의 불일치

DB 기록에는 성공했지만 Redis 발행에 실패하면 작업이 대기열에 들어가지 않을 수 있다. 이를 방지하기 위해 작업 테이블과 Outbox 테이블을 같은 DB 트랜잭션에서 저장하고, 별도 Publisher가 미발행 Outbox 이벤트를 Redis로 전달한 뒤 발행 완료로 표시한다.

### 워커 장애

워커는 결과 저장이 완료되기 전까지 메시지를 승인하지 않는다. 처리 도중 종료된 메시지는 Pending 상태로 남고, 복구 프로세스가 유휴 시간을 확인한 뒤 `XAUTOCLAIM`으로 다른 워커에 전달한다.

### 과도한 동시 추론

AI 워커의 Consumer 수와 프로세스 동시성으로 실행량을 제한한다. 모델 메모리와 CPU 사용량을 기준으로 워커당 동시 실행 수를 고정하고, 대기 작업 증가는 API 서버가 아니라 AI 워커만 수평 확장하여 처리한다.

## 6. 작업 상태

| 상태 | 의미 |
|---|---|
| `PENDING` | DB 등록 및 큐 전달 대기 |
| `QUEUED` | Redis Stream 발행 완료 |
| `PROCESSING` | AI 워커가 처리 중 |
| `SUCCEEDED` | 결과 저장 완료 |
| `FAILED` | 재시도 후 최종 실패 |

상태 변경은 이전 상태를 조건으로 갱신한다. 이미 종료 상태인 작업은 다시 처리 상태로 변경하지 않는다.

## 7. 오류 처리와 운영 기준

- 네트워크 단절과 일시적인 DB 오류는 지수 백오프로 제한된 횟수만 재시도한다.
- 파일 누락, 지원하지 않는 이미지, 모델 입력 오류는 재시도하지 않고 실패 처리한다.
- 재시도 한도를 넘긴 이벤트는 `prediction:tasks:dlq`로 이동하고 작업을 `FAILED`로 기록한다.
- 로그에는 `job_id`, `record_id`, `message_id`, `worker_id`, `ai_model`을 포함한다.
- 대기열 길이, Pending 수, 작업 처리 시간, 성공률, 재시도 수, DLQ 수를 모니터링한다.
- Redis는 AOF 영속화를 사용하고 외부에서 직접 접근할 수 없도록 내부 네트워크에 둔다.
- X-ray 원본이나 환자 개인정보는 이벤트에 넣지 않고 DB 식별자와 추론에 필요한 최소 메타데이터만 전달한다.

## 8. 기존 API 변경 방향

- 예측 생성 API는 동기 결과 대신 작업 접수 결과를 `202 Accepted`로 반환한다.
- 예측 작업 상태 조회 API를 추가한다.
- 기존 예측 결과 조회 API는 완료된 결과를 조회하는 용도로 유지한다.
- `prediction_service`에서 모델 실행 책임을 제거하고 작업 생성 및 조회 책임만 남긴다.
- `worker/model.py`는 AI 워커 프로세스에서만 import하고 실행한다.
- Docker Compose에 Redis, AI Worker, Outbox Publisher 서비스를 추가한다.

## 9. 기대 효과

- 장시간 추론과 API 응답 처리가 분리된다.
- 동일 진료기록의 중복 추론과 중복 저장을 억제한다.
- 워커 장애 후에도 미완료 작업을 복구할 수 있다.
- API와 AI 워커를 부하 특성에 맞게 독립적으로 확장할 수 있다.
- 재시도와 실패 작업이 명시적으로 관리되어 운영 상태를 추적할 수 있다.
