## 현재 프로젝트 구조

과제 안내의 예시 구조와 실제 프로젝트 구조에는 일부 차이가 있다. 실제 프로젝트에서는 `static/`이 `app/` 내부가 아니라 프로젝트 루트에 있으며, `media/`는 애플리케이션 실행 시 `app/main.py`가 프로젝트 루트에 생성한다.


`__init__.py`는 해당 디렉터리를 Python 패키지로 인식하게 하는 파일이다. 현재 `models`, `repositories`, `schemas`, `services`에는 빈 `__init__.py`만 있으며, 이후 단계에서 실제 기능 파일을 추가할 예정이다.

## 1. 주요 디렉터리의 역할

### 1.1 `app/core/`

애플리케이션 전체에서 공통으로 사용하는 핵심 설정을 관리한다. 특정 API 기능에 종속되지 않고 여러 기능에서 함께 사용하는 코드를 둔다.

현재 포함된 내용:

- `config.py`: `.env`의 환경변수를 읽어 애플리케이션 설정 객체를 생성한다.
- `db/databases.py`: DB URL, 비동기 SQLAlchemy 엔진, 세션 팩토리, 공통 `Base`를 정의한다.
- `db/models.py`: UUID, 생성·수정 시간, 소프트 삭제 기능을 재사용할 수 있는 Mixin을 정의한다.

이 디렉터리에는 향후 인증, 예외 처리, 보안, 로깅처럼 프로젝트 전체에서 공통으로 사용하는 기능을 추가할 수 있다.

### 1.2 `app/models/`

데이터베이스 테이블을 Python 클래스로 표현하는 SQLAlchemy ORM 모델을 작성한다.

각 모델 파일에 작성할 내용:

- `__tablename__`: 실제 DB 테이블 이름
- Primary Key와 일반 컬럼
- 컬럼의 데이터 타입과 길이
- `nullable`, `unique`, `default` 등의 제약조건
- `ForeignKey`: 다른 테이블과 연결되는 외래 키
- `relationship`: Python 객체 수준의 테이블 관계
- 필요한 경우 UUID, Timestamp, SoftDelete Mixin 상속

예상 파일 구성은 ERD 분석 후 결정한다.

```text
app/models/
├── __init__.py
├── user.py
├── patient.py
└── medical_record.py
```

현재는 `__init__.py`만 존재하며 실제 모델은 아직 작성되지 않았다. 과제 안내의 `apps/models/`는 현재 프로젝트 구조상 `app/models/`를 의미한다.

### 1.3 `app/repositories/`

데이터베이스에 직접 접근하는 코드를 작성한다. SQLAlchemy `AsyncSession`을 사용하여 데이터를 생성, 조회, 수정, 삭제하는 CRUD 작업을 담당한다.

작성할 내용의 예:

- 회원 ID 또는 이메일로 조회
- 환자 목록 조회
- 새로운 진료 기록 저장
- 회원 정보 수정
- 논리 삭제 또는 실제 삭제
- 여러 테이블을 결합한 조회

Repository는 HTTP 요청이나 응답 형식을 직접 다루지 않는다. DB 작업에 집중하고, Service 계층에서 재사용할 수 있도록 작성한다.

### 1.4 `app/schemas/`

FastAPI가 받는 요청 데이터와 반환하는 응답 데이터의 형식을 Pydantic 모델로 정의한다.

작성할 내용의 예:

- 회원 생성 요청 `UserCreate`
- 회원 수정 요청 `UserUpdate`
- 회원 조회 응답 `UserResponse`
- 필수 입력값과 선택 입력값 구분
- 문자열 길이, 숫자 범위, 이메일 형식 등의 검증
- 응답에서 비밀번호와 같은 민감한 필드 제외

현재 Stage 2 실습에서는 `app/apis/schema.py`에 조회용 `User` 스키마가 작성되어 있다. 프로젝트의 레이어드 구조를 계속 적용한다면 이후 실제 서비스용 Pydantic 스키마는 `app/schemas/`에서 기능별로 관리하는 것이 역할 구분에 더 적합하다.

### 1.5 `app/services/`

프로젝트의 업무 규칙과 핵심 비즈니스 로직을 작성한다. API와 Repository 사이에서 요청을 처리할 순서를 결정한다.

작성할 내용의 예:

- 회원 가입 시 이메일 중복 여부 확인
- 비밀번호 해시 처리
- 폐렴 판독 결과에 따른 상태 결정
- 환자 등록 가능 여부 확인
- 여러 Repository의 작업을 하나의 트랜잭션으로 처리

Service는 API 경로나 HTML 화면을 직접 다루지 않고, DB 세부 쿼리는 Repository에 위임한다.

### 1.6 `app/apis/`

클라이언트의 HTTP 요청을 받는 FastAPI Router를 작성한다.

작성할 내용:

- `APIRouter` 생성과 URL prefix 설정
- GET, POST, PATCH, DELETE 등의 endpoint 정의
- Path, Query, Request Body 데이터 수신
- Pydantic Schema를 이용한 요청 검증
- Service 호출
- HTTP 상태 코드와 응답 형식 정의
- 존재하지 않는 데이터 등에 대한 `HTTPException` 처리

현재 파일:

- `practice_apis.py`: Stage 2에서 작성한 회원 조회, 수정, 삭제 실습 API
- `schema.py`: Stage 2 조회 API의 응답 모델

현재 `practice_apis.py`의 Router는 `/practice_api` prefix를 사용하고, `app/main.py`에 등록되어 있다.

## 2. 주요 파일의 역할

디렉터리가 "무엇을 어디에 두는가"를 정한다면, 이 파일들은 "앱을 어떻게 실행하고 무엇에 의존하는가"를 정한다. 프로젝트를 실행하고 설정하는 데 중심이 되는 파일들이다.

### 2.1 `app/main.py`

FastAPI 애플리케이션의 진입점이다. 서버를 실행하면 이 파일의 `app` 객체가 구동된다.

주요 역할:

- `app = FastAPI()`로 애플리케이션 인스턴스를 생성한다.
- `app.include_router()`로 각 Router를 앱에 등록한다. 현재는 `app/apis/practice_apis.py`의 Router가 등록되어 있다.
- `static/`, `media/` 폴더를 각각 `/static`, `/media` 경로에 마운트하여 정적 파일과 업로드 파일을 제공한다. 폴더가 없으면 실행 시 생성한다.
- `/healthcheck` 엔드포인트로 서버 상태를 확인하고, 그 외 경로는 프론트엔드 `index.html`을 반환한다.

실행은 `uvicorn app.main:app` 명령으로 이 파일의 `app`을 지정해 띄운다. 새 Router를 추가할 때는 이 파일에서 `include_router`로 등록해야 요청이 실제로 연결된다.

### 2.2 `app/core/config.py`

애플리케이션 설정값을 관리하는 파일이다. `pydantic-settings`의 `BaseSettings`를 사용해 `.env`의 값을 읽어 설정 객체로 만든다.

주요 역할:

- `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` 같은 DB 접속 정보를 `.env`에서 불러온다.
- 생성된 `settings` 객체를 `databases.py` 등 다른 코드에서 가져다 사용한다.
- 접속 정보나 비밀번호를 코드에 직접 적지 않고 `.env`에서 주입받게 하여, 값이 바뀌어도 코드를 고치지 않게 한다.

`.env`는 저장소에 올리지 않으며(`.gitignore`로 제외), `.env.example`을 참고해 각자 로컬에서 생성한다.

### 2.3 `pyproject.toml`

프로젝트의 메타 정보와 의존성 목록을 정의하는 파일이다. `uv`가 이 파일을 기준으로 패키지를 설치한다.

주요 내용:

- `requires-python`: 프로젝트가 사용하는 Python 버전
- `dependencies`: 프로젝트가 필요로 하는 패키지 목록. 현재 `fastapi`, `sqlalchemy[asyncio]`, `alembic`, `asyncmy`, `pydantic-settings`, `uuid6`, `cryptography` 등이 선언되어 있다.

새 패키지가 필요하면 이 파일의 `dependencies`에 추가한 뒤 설치한다.

### 2.4 `uv.lock`

`pyproject.toml`의 의존성이 실제로 설치된 **정확한 버전**을 고정해 기록하는 파일이다.

- `pyproject.toml`이 "무엇이 필요한가"라면, `uv.lock`은 "정확히 어떤 버전이 설치됐는가"를 담는다.
- 팀원 모두 같은 잠금 파일을 사용하므로 동일한 버전이 설치되어, 환경 차이로 생기는 오류를 줄인다.
- 직접 손으로 수정하지 않고, 패키지를 추가하거나 바꾸면 `uv`가 자동으로 갱신한다.

## 3. 데이터베이스 연결 설정 — `app/core/db/databases.py`

이 파일은 MySQL 데이터베이스와의 비동기 연결에 필요한 엔진, 세션 팩토리, ORM 공통 베이스를 한 곳에 정의한다.

### 3.1 데이터베이스 URL 구성

```python
DATABASE_PREFIX = "mysql+asyncmy://"
DATABASE_URI = f"{settings.DB_USER}:{settings.DB_PASSWORD}@{settings.DB_HOST}:{settings.DB_PORT}/{settings.DB_NAME}"
DATABASE_URL = f"{DATABASE_PREFIX}{DATABASE_URI}"
```

`settings`는 `app/core/config.py`의 `Settings` 객체이다. `.env` 파일에 정의된 환경변수(`DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`)를 자동으로 읽어 주입한다. `.env`가 없으면 `Settings`에 정의된 기본값을 사용한다.

`mysql+asyncmy://` 접두어는 SQLAlchemy에게 "MySQL 데이터베이스를 비동기 드라이버(`asyncmy`)로 연결하라"는 의미이다. 동기 드라이버(`pymysql`)를 사용하면 접두어가 `mysql+pymysql://`이 된다.

최종 URL 형태는 다음과 같다.

```
mysql+asyncmy://root:password1234@localhost:3306/ai_health
```

### 3.2 비동기 엔진 생성

```python
async_engine = create_async_engine(DATABASE_URL, echo=False, future=True)
```

엔진(Engine)은 데이터베이스와의 실제 연결을 관리하는 객체이다. 내부적으로 커넥션 풀을 유지하여 매 요청마다 새로 연결을 맺지 않고 기존 연결을 재사용한다.

- `echo=False`: SQLAlchemy가 실행하는 SQL 쿼리를 콘솔에 출력하지 않는다. `True`로 바꾸면 디버깅 시 실행 쿼리를 확인할 수 있다.
- `future=True`: SQLAlchemy 2.0 스타일 API를 사용하도록 설정한다.

### 3.3 비동기 세션 팩토리 생성

```python
AsyncSessionLocal = async_sessionmaker(bind=async_engine, autoflush=False, expire_on_commit=False)
```

세션(Session)은 데이터베이스와의 대화 단위이다. 쿼리를 보내고 결과를 받는 작업은 세션을 통해 이루어진다. `async_sessionmaker`는 세션을 찍어내는 공장 역할을 한다. `AsyncSessionLocal()`을 호출하면 새로운 `AsyncSession` 객체가 만들어진다.

- `bind=async_engine`: 이 세션 팩토리가 위에서 만든 엔진에 연결된다는 것을 명시한다.
- `autoflush=False`: 세션에서 변경된 내용이 쿼리 전에 자동으로 DB에 반영(`flush`)되지 않는다. `commit()` 또는 명시적 `flush()` 호출 시에만 반영된다.
- `expire_on_commit=False`: `commit()` 후 세션이 들고 있는 객체들이 만료(expired) 처리되지 않는다. `True`면 커밋 이후 객체에 접근할 때 DB에 다시 SELECT를 날린다. 비동기 환경에서는 이 재조회가 예상치 못한 `MissingGreenlet` 오류를 유발할 수 있어 `False`로 설정하는 것이 일반적이다.

### 3.4 ORM 공통 베이스

```python
Base = declarative_base()
```

`Base`는 모든 SQLAlchemy ORM 모델이 상속받는 공통 부모 클래스이다. `app/models/`에 작성할 모델 클래스들은 이 `Base`를 상속받아야 Alembic이 테이블 변경사항을 추적할 수 있다.

### 3.5 세션 의존성 주입 함수

```python
async def async_get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as db:
        yield db
```

FastAPI의 `Depends(async_get_db)`를 API 함수의 파라미터에 선언하면, 요청이 들어올 때마다 이 함수가 실행되어 세션 객체 `db`가 자동으로 주입된다.

`async with` 블록 덕분에 `yield db` 이후 API 처리가 끝나면 세션이 자동으로 닫힌다. 개발자가 직접 `session.close()`를 호출하지 않아도 된다.

사용 예:

```python
from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession
from app.core.db.databases import async_get_db

@router.get("/users")
async def get_users(db: AsyncSession = Depends(async_get_db)):
    # db를 사용해 쿼리 실행
    ...
```

## **4. Alembic 마이그레이션 방법**

Alembic은 SQLAlchemy ORM 모델의 변경 사항을 마이그레이션 파일로 기록하고, 이를 실제 데이터베이스 스키마에 적용하는 도구이다.

현재 `alembic/env.py`에서는 다음과 같이 SQLAlchemy의 `Base.metadata`를 Alembic에 연결한다.

```python
from app.core.db.databases import Base, DATABASE_URL
from app import models

config.set_main_option("sqlalchemy.url", DATABASE_URL)
target_metadata = Base.metadata
```

`DATABASE_URL`을 통해 데이터베이스에 연결하고, `Base.metadata`에 등록된 모델을 기준으로 테이블 및 컬럼 변경 사항을 탐지한다.

### **4-1. SQLAlchemy 모델 작성**

ERD를 기준으로 각 테이블에 대응하는 SQLAlchemy 모델을 작성한다.

```python
class User(Base):
    __tablename__ = "users"

    id = mapped_column(
        Integer,
        primary_key=True,
        autoincrement=True,
    )
```

현재 프로젝트에서는 모델별로 파일을 분리하여 관리한다.

```
app/models/
├── user.py
├── patient.py
├── medical_record.py
├── xray_image.py
├── ai_analysis_result.py
└── __init__.py
```

### **4-2. 모델 import**

Alembic은 `Base.metadata`에 등록된 모델만 인식한다.

따라서 `app/models/__init__.py`에서 모든 모델을 import해야 한다.

```python
from app.models.user import User
from app.models.patient import Patient
from app.models.medical_record import MedicalRecord
from app.models.xray_image import XrayImage
from app.models.ai_analysis_result import AIAnalysisResult
```

모델 파일은 존재하지만 import되지 않은 경우, Alembic이 해당 테이블을 탐지하지 못할 수 있다.

### **4-3. SQLite 데이터베이스 설정**

이번 프로젝트에서는 SQLite를 사용한다.

`.env` 파일에 다음과 같이 데이터베이스 연결 정보를 작성한다.

```
DATABASE_URL=sqlite+aiosqlite:///./ai_health.db
```

SQLite는 별도의 데이터베이스 서버가 필요하지 않으므로 MySQL과 달리 `DB_HOST`, `DB_PORT` 또는 MySQL Docker 컨테이너를 실행할 필요가 없다.

마이그레이션을 적용하면 프로젝트 경로에 `ai_health.db` 파일이 생성된다.

### **4-4. 마이그레이션 파일 자동 생성**

SQLAlchemy 모델을 작성하거나 수정한 후 다음 명령을 실행한다.

```bash
uv run alembic revision --autogenerate -m "create initial tables"
```

실행하면 `alembic/versions/` 디렉터리에 새로운 revision 파일이 생성된다.

예를 들면 다음과 같다.

```
alembic/
└── versions/
    └── xxxx_create_initial_tables.py
```

### **4-5. 생성된 마이그레이션 파일 검토**

자동 생성된 마이그레이션 파일의 `upgrade()`와 `downgrade()`를 확인한다.

```python
def upgrade() -> None:
    op.create_table(...)

def downgrade() -> None:
    op.drop_table(...)
```

`upgrade()`는 데이터베이스 스키마를 다음 버전으로 변경하고, `downgrade()`는 이전 버전으로 되돌린다.

다음 변경 사항은 자동 생성 결과를 반드시 검토해야 한다.

- 컬럼 이름 변경
- 테이블 이름 변경
- 컬럼 타입 변경
- 기존 데이터가 있는 컬럼에 `nullable=False` 추가
- 컬럼 삭제
- 기본값 변경
- 외래키와 삭제 정책 변경

Alembic은 컬럼 이름 변경을 기존 컬럼 삭제와 새로운 컬럼 생성으로 판단할 수 있다. 이 경우 기존 데이터가 손실될 수 있으므로 적용 전에 마이그레이션 파일을 확인해야 한다.

### **4-6. 데이터베이스에 마이그레이션 적용**

다음 명령으로 최신 마이그레이션을 실제 데이터베이스에 적용한다.

```bash
uv run alembic upgrade head
```

정상적으로 실행되면 SQLite 데이터베이스에 다음 테이블이 생성된다.

```
users
patients
medical_records
xray_images
ai_analysis_results
alembic_version
```

`alembic_version`은 현재 적용된 마이그레이션 revision을 Alembic이 기록하는 테이블이다.

### **4-7. 마이그레이션 상태 확인**

현재 데이터베이스에 적용된 revision을 확인한다.

```bash
uv run alembic current
```

전체 마이그레이션 이력을 확인한다.

```bash
uv run alembic history
```

최신 revision과 현재 DB 상태를 함께 확인하려면 다음 명령도 사용할 수 있다.

```bash
uv run alembic heads
```

### **4-8. 직전 마이그레이션 취소**

직전 마이그레이션을 한 단계 되돌리려면 다음 명령을 사용한다.

```bash
uv run alembic downgrade -1
```
다만 컬럼이나 테이블을 삭제하는 downgrade는 데이터 손실을 발생시킬 수 있으므로 실제 데이터가 있는 환경에서는 적용 전에 반드시 검토해야 한다.

## 5. API 구현 흐름

### 5.1 전체 요청 처리 흐름

클라이언트의 HTTP 요청이 응답으로 돌아오기까지 아래 순서로 계층을 통과한다.

```text
클라이언트 (브라우저 / 앱)
    │  ① HTTP 요청 (예: POST /users)
    ▼
app/main.py ─ FastAPI 앱이 요청을 받아 등록된 Router로 전달
    ▼
app/apis/ ─ ② URL과 HTTP 메서드가 일치하는 endpoint 매칭
    ▼
app/schemas/ ─ ③ Pydantic이 요청 Body를 검증 (형식 오류 시 422 자동 응답)
    ▼
app/services/ ─ ④ 비즈니스 로직 수행 (중복 확인, 해싱, 상태 결정 등)
    ▼
app/repositories/ ─ ⑤ AsyncSession으로 DB 쿼리 실행 (CRUD)
    ▼
app/models/ ─ ⑥ SQLAlchemy 모델 ↔ DB 테이블 매핑
    ▼
Database
    │  조회/저장 결과가 역순으로 반환
    ▼
app/schemas/ ─ ⑦ response_model에 따라 응답 스키마로 변환 (민감 정보 제외)
    ▼
클라이언트 ─ ⑧ JSON 응답 수신 (예: 201 Created)
```

핵심 원칙은 **각 계층이 자신의 바로 아래 계층만 호출한다**는 것이다. API가 Repository를 직접 호출하거나, Service가 HTTP 요청 객체를 다루지 않는다. 역할이 분리되어 있으므로 수정 범위가 명확해지고 계층별 테스트가 쉬워진다.

### 5.2 계층별 예시 코드 (회원 가입 시나리오)

`POST /users` 요청으로 회원을 생성하는 상황을 가정하고, 각 계층에 작성될 코드를 순서대로 살펴본다. 현재 프로젝트는 비동기 SQLAlchemy(`AsyncSession`)를 사용하므로 예시도 `async` 기준으로 작성한다.

#### ① schemas — 요청/응답 데이터 형식 정의

```python
# app/schemas/user.py
from pydantic import BaseModel, EmailStr

class UserCreate(BaseModel):        # 요청용
    email: EmailStr
    password: str

class UserResponse(BaseModel):      # 응답용 (비밀번호 미포함)
    id: int
    email: EmailStr

    class Config:
        from_attributes = True      # SQLAlchemy 객체 → 스키마 자동 변환
```

요청 스키마와 응답 스키마를 분리하는 이유는 응답에 비밀번호 같은 민감한 필드가 노출되는 것을 원천 차단하기 위해서이다.

#### ② repositories — DB 접근

```python
# app/repositories/user.py
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession
from app.models.user import User

async def get_user_by_email(db: AsyncSession, email: str) -> User | None:
    result = await db.execute(select(User).where(User.email == email))
    return result.scalar_one_or_none()

async def create_user(db: AsyncSession, email: str, hashed_pw: str) -> User:
    user = User(email=email, password=hashed_pw)
    db.add(user)
    await db.commit()
    await db.refresh(user)          # DB가 생성한 id 등을 다시 읽어옴
    return user
```

#### ③ services — 비즈니스 로직

```python
# app/services/user.py
from fastapi import HTTPException
from sqlalchemy.ext.asyncio import AsyncSession
from app.repositories import user as user_repo
from app.schemas.user import UserCreate

async def register_user(db: AsyncSession, user_data: UserCreate):
    # 규칙 1: 이메일 중복 금지
    if await user_repo.get_user_by_email(db, user_data.email):
        raise HTTPException(status_code=409, detail="이미 존재하는 이메일입니다")
    # 규칙 2: 비밀번호는 해싱 후 저장
    hashed = hash_password(user_data.password)
    return await user_repo.create_user(db, user_data.email, hashed)
```

"어떤 조건에서 실패시키고, 어떤 가공을 거쳐 저장하는가"와 같은 업무 규칙이 모두 이 계층에 모인다.

#### ④ apis — endpoint 정의

```python
# app/apis/user.py
from fastapi import APIRouter, Depends
from sqlalchemy.ext.asyncio import AsyncSession
from app.core.db.databases import get_db
from app.schemas.user import UserCreate, UserResponse
from app.services import user as user_service

router = APIRouter(prefix="/users", tags=["users"])

@router.post("", response_model=UserResponse, status_code=201)
async def create_user(user_data: UserCreate, db: AsyncSession = Depends(get_db)):
    return await user_service.register_user(db, user_data)
```

Router는 최대한 얇게 유지한다. 요청을 받고, Service를 호출하고, 결과를 반환하는 역할만 한다. `Depends(get_db)`가 `app/core/db/databases.py`의 세션을 주입하는 지점이며, `response_model=UserResponse` 설정으로 반환된 SQLAlchemy 객체가 응답 스키마로 자동 변환된다.

#### ⑤ main.py — Router 등록

```python
# app/main.py
from fastapi import FastAPI
from app.apis.user import router as user_router

app = FastAPI()
app.include_router(user_router)
```

`include_router`로 등록해야 해당 URL 경로가 실제로 활성화된다. 현재 프로젝트에서는 `practice_apis.py`의 Router가 `/practice_api` prefix로 이미 이 방식으로 등록되어 있다.

### 5.3 개발 시 작성 순서

요청 처리 흐름과 달리, 실제 개발은 데이터 계층부터 바깥쪽으로 진행하는 것이 일반적이다.

1. `app/models/` — 테이블 모델 정의 후 Alembic 마이그레이션 수행
2. `app/schemas/` — 요청/응답 스키마 정의
3. `app/repositories/` — CRUD 함수 작성
4. `app/services/` — 비즈니스 로직 작성
5. `app/apis/` — Router 작성
6. `app/main.py` — Router 등록
7. Swagger UI(`http://localhost:8000/docs`)에서 endpoint 직접 호출하여 테스트

즉 "데이터 → 로직 → 인터페이스" 순서로, 안쪽 계층에서 바깥쪽 계층으로 만들어 나간다. FastAPI는 서버 실행 시 `/docs` 경로에 API 문서를 자동 생성하므로 별도 도구 없이 브라우저에서 바로 테스트할 수 있다.

### 5.4 계층을 분리하는 이유

- **유지보수**: DB를 교체하면 Repository만, 가입 규칙이 바뀌면 Service만 수정하면 된다. 변경의 영향 범위가 한 계층으로 한정된다.
- **테스트**: Service를 테스트할 때 Repository를 가짜(mock)로 대체할 수 있어 DB 없이도 로직 검증이 가능하다.
- **협업**: 계층별로 담당을 나누어 동시에 작업해도 코드 충돌이 적다. 팀 프로젝트에서 특히 유리한 구조이다.
