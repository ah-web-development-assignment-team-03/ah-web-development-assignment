# 9일차 - 동시성 문제 해결을 위한 아키텍처 설계

## 1. 배경 — 왜 동시성 문제가 발생하는가

현재 서비스 흐름은 다음과 같다.

```
클라이언트 → FastAPI → AI 모델 추론 → 응답
```

폐렴 예측 모델(densenet121 5-fold 앙상블)의 CPU 추론 시간은 약 1.7~2.0초로 확인되었다.
FastAPI가 이 추론을 요청 처리 흐름 안에서 직접 수행하면 다음 문제가 발생한다.

- 추론이 끝날 때까지 해당 요청을 처리하는 자원이 점유된다.
- 여러 사용자가 동시에 예측을 요청하면 대기 시간이 누적되어 NFR-PRED-002(API 3초 이내 응답)를 지키기 어려워진다.
- "요청 응대"와 "무거운 연산"이 한 프로세스 안에서 경합하는 상태 — 이것이 동시성(concurrency) 문제다.

## 2. 해결 방향 — Event-Driven Architecture

요청을 받는 역할과 실제 연산을 수행하는 역할을 분리한다.

- FastAPI는 예측 요청을 받으면 작업을 큐에 등록만 하고 즉시 응답한다.
- 별도 프로세스인 AI 워커가 큐에서 작업을 꺼내 추론을 수행한다.
- FastAPI와 AI 워커는 Redis를 매개로 통신한다.

이벤트(요청 발생)가 큐에 쌓이고, 워커가 이를 소비(consume)하여 처리하는 구조이므로 Event-Driven Architecture라 부른다.

## 3. Redis Streams vs Celery+Redis 비교

| 항목 | Redis Streams | Celery + Redis |
|---|---|---|
| 구현 방식 | Redis 자체 기능으로 직접 구현 | Celery가 큐잉·워커 실행을 프레임워크로 제공(Redis는 브로커 역할) |
| 재시도/실패 처리 | 기본 제공 안 됨 (consumer group ack 직접 관리) | 내장 기능 (자동 재시도, 타임아웃 설정) |
| 결과 저장 | 직접 DB에 쓰는 로직 작성 필요 | result backend로 결과 자동 저장/조회 가능 |
| 학습 곡선 | 낮음 — Redis 명령어 몇 개만 익히면 됨 | 중간 — Celery 설정(worker, broker, task) 개념 추가 학습 필요 |
| 운영 복잡도 | 낮음 — 별도 워커 프레임워크 불필요 | 중간 — Celery worker 프로세스/컨테이너 추가 관리 |
| 적합한 상황 | 단순한 이벤트 로그, 가벼운 큐 | 재시도·실패 처리가 중요한 백그라운드 작업, 팀 협업 |

## 4. 아키텍처 설계 (excalidraw)

![Event-Driven Architecture 설계](images/9일차/event-driven-architecture.png)

### 컴포넌트별 역할

- **클라이언트**: 예측 요청(POST)을 보내고, 결과를 폴링 또는 콜백으로 수신
- **FastAPI 서버**: 요청을 접수한 뒤 작업을 Redis 큐에 등록(PUSH)하고 즉시 응답 반환. AI 워커와 물리적으로 분리된 별도 프로세스로 동작
- **Redis (작업 대기열)**: FastAPI가 등록한 작업을 보관, AI 워커가 이를 꺼내감(POP)
- **AI 워커**: Redis에서 작업을 꺼내 별도 프로세스에서 추론을 수행, 완료 후 결과를 DB에 저장
- **DB**: 예측 결과를 저장, 클라이언트의 폴링/콜백 요청에 결과 제공

### 설계 원칙 (완료 조건 반영)

- FastAPI(요청 처리)와 AI 워커(추론 수행)의 작업이 명확히 분리되어 있다.
- Redis를 통해 작업 대기열을 관리하여 동시 요청이 몰려도 FastAPI 응답 지연이 발생하지 않는다.
