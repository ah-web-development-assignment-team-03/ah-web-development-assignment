# 9일차 - 동시성 문제 해결을 위한 아키텍처 설계

> 본 문서는 현재 동기(inline) 방식으로 동작하는 AI 폐렴 예측의 동시성 문제를 정리하고,
> 이를 해결하기 위한 Event-Driven Architecture(EDA) 목표 구조를 설계한다.
> **이번 단계는 설계 문서이며, 앱 코드·의존성(redis/celery 등)은 변경하지 않는다.**
> 인용한 코드 사실은 현재 리포지토리(`app/`, `worker/`)를 직접 확인해 근거로 삼았다.

---

## 1. 현재 구조와 동시성 문제

### 1.1 현재 예측 실행 흐름

폐렴 예측은 `POST /api/v1/medical-records/{record_id}/predictions` 요청이
`app/apis/predictions.py`의 핸들러를 거쳐 `app/services/prediction_service.py`의
`run_prediction()`에서 처리된다. 흐름은 다음과 같다.

1. **진료기록 확인** — `get_medical_record_by_id()`로 존재를 확인하고, 없으면 404.
2. **X-ray 확인** — `get_xray_image_by_record_id()`로 이미지를 확인하고, 없으면 404.
3. **캐시 조회** — `get_cached_result(db, record_id, MODEL_TAG)`로 이미 저장된 결과가 있으면
   추론 없이 그 결과를 `cached=True`로 반환한다. (`MODEL_TAG = "v7_densenet121_5fold"`)
4. **추론 수행** — 캐시가 없으면 `image_path`를 만들어
   `await anyio.to_thread.run_sync(predict, image_path, abandon_on_cancel=True)`로
   **동기 추론 함수 `predict()`를 워커 스레드에 위임**해 실행한다.
5. **저장** — `save_result()` 후 `db.commit()`으로 결과를 저장하고 `cached=False`로 반환한다.

`predict()`(`worker/model.py`)는 `@torch.no_grad()`가 붙은 **동기 함수(`def`)** 로,
3 scale × 5 fold = 15회의 CPU 추론을 수행한다. 모델은 `load_models()`가
모듈 전역 `_FOLD_MODELS`에 5-fold를 **프로세스당 1회** 로드해 재사용하며,
이 로드는 `app/main.py`의 `lifespan`에서 `anyio.to_thread.run_sync(load_models)`로
**API 서버 기동 시** 이루어진다.

요청 핸들러는 위 처리를 `async with asyncio.timeout(PREDICTION_API_TIMEOUT_SECONDS)`
(현재 `3.0`초, NFR-PRED-002) 안에서 감싸고, 초과 시 `HTTP 504 GATEWAY_TIMEOUT`을 반환한다.

### 1.2 문제 ① 중복 추론

같은 `record_id`에 **동시에** 예측 요청이 오면, 두 요청 모두 3단계(캐시 조회)에서
아직 저장된 결과가 없으므로 **캐시 미스**가 되어 각자 4단계의 무거운 추론을 수행한다.
두 요청이 5단계 저장에 이르면, `AIAnalysisResult`에 걸린
`UniqueConstraint("record_id", "ai_model")`(`uq_ai_analysis_results_record_model`) 때문에
뒤늦게 저장하는 쪽이 `IntegrityError`를 만난다. 현재 코드는 이를 잡아
`get_cached_result()`로 먼저 저장된 결과를 다시 읽어 반환하며 요청 자체는 성공한다.

즉 **정합성은 유지되지만 추론이 중복 실행**된다. 이는 사후 수습(무결성 제약 → 재조회)일 뿐,
동시 추론 자체를 막지는 못한다.

### 1.3 문제 ② 스레드풀 점유

`predict()`는 CPU-bound 동기 작업이라 이벤트 루프를 막지 않도록
`anyio.to_thread.run_sync`로 스레드에 위임된다. 그러나 anyio가 관리하는
워커 스레드 풀에는 한도가 있어, 예측 요청이 몰리면 스레드가 추론으로 점유된다.
추론은 CPU-bound이므로 파이썬 GIL의 영향으로 **스레드를 늘려도 병렬 처리량이
비례해 늘지 않는다.** 결과적으로 다른 요청이 스레드 위임이 필요한 작업을 할 때
대기가 생겨 다른 엔드포인트 응답에도 영향을 줄 수 있다.

> anyio 기본 스레드 한도의 구체 수치는 버전·설정에 따라 달라질 수 있어 여기서 단정하지 않는다.
> 요점은 "한정된 스레드 풀을 무거운 추론이 점유한다"는 구조적 사실이다.

### 1.4 문제 ③ 응답 지연

추론이 끝날 때까지 **HTTP 요청이 열린 채 대기**한다. 그래서 이미 3초 타임아웃과
504 방어 코드가 들어가 있다. 프론트엔드(record-detail 화면의 "AI 예측 실행" 버튼 →
`handlePredict()` → `apis.predictPneumonia()`)도 응답이 올 때까지 대기한다.
추론 시간이 타임아웃에 가까워질수록 사용자 대기와 실패(504) 위험이 커진다.

### 1.5 문제 ④ 자원 결합

`load_models()`가 5-fold 모델을 **API 프로세스 메모리에 상주**시킨다. 따라서 트래픽 대응을
위해 API 서버(프로세스)를 늘리면 모델도 프로세스마다 함께 로드되어,
**API 확장 단위와 모델(추론) 확장 단위가 묶인다.** 요청 처리량 때문에 API를 늘리는데
무거운 모델도 같이 늘어나고, 반대로 추론 자원만 늘리는 것도 어렵다.

## 2. Event-Driven Architecture 학습 내용

### 2.1 EDA 개념과 적합성

Event-Driven Architecture는 작업을 **요청 수신**과 **실제 처리**로 분리하고,
그 사이를 **이벤트/메시지 큐**로 연결하는 패턴이다. 생산자(API)는 "예측을 해달라"는
이벤트를 큐에 넣고 즉시 응답하며, 소비자(Worker)가 큐에서 이벤트를 꺼내 처리한다.

무거운 AI 추론은 (1) 실행 시간이 길고, (2) CPU를 오래 점유하며, (3) 요청량이 급증할 수 있어
동기 처리에 부적합하다. 이벤트로 분리하면 API는 빠르게 응답하고, 처리량은 소비자(워커)
수로 독립 조절할 수 있어 이 워크로드에 적합하다.

### 2.2 Redis 기반 작업 대기열 방식 비교

| 방식 | 개요 | 내구성/재처리 | 중복 방지 | 특징 |
|---|---|---|---|---|
| **List (`LPUSH`/`BRPOP`)** | 리스트를 큐로 사용, 블로킹 팝으로 소비 | 팝하면 메시지가 사라져 처리 중 워커가 죽으면 유실 가능 | 별도 키로 직접 구현해야 함 | 가장 단순, 소규모에 충분 |
| **Streams (Consumer Group)** | append-only 로그 + 소비자 그룹, `XREADGROUP`/`XACK` | ACK 전까지 pending으로 남아 재처리(claim) 가능 | 소비자 그룹으로 한 메시지 1회 처리 + 미확인 재분배 | 내구성·재처리에 유리, 상대적으로 복잡 |
| **Pub/Sub** | 채널 발행/구독, fire-and-forget | 구독자가 없으면 메시지 유실, 저장 안 함 | 없음 | 실시간 알림에 적합, 작업 큐로는 부적합 |

작업 큐에는 유실 방지와 재처리가 중요하므로 **Streams(Consumer Group)** 가 가장 견고하다.
소규모/학습 목적에서는 List(BRPOP)로 시작해도 되며, Pub/Sub은 "작업 분배"보다
"결과 알림(예: 완료 이벤트 브로드캐스트)"에 어울린다.

### 2.3 도구 선택지 비교

| 도구 | 개요 | 러닝커브 | 재시도 | 모니터링 |
|---|---|---|---|---|
| **Celery** | 성숙한 분산 태스크 큐(브로커: Redis/RabbitMQ) | 높음(개념·설정 많음) | 강력(재시도·백오프·라우팅) | Flower 등 생태계 풍부 |
| **RQ** | Redis 전용의 단순 큐 | 낮음 | 기본 제공(제한적) | rq-dashboard |
| **arq** | asyncio 친화 Redis 큐(FastAPI와 async 궁합) | 중간 | 지원 | 상대적으로 가벼움 |
| **Redis Streams 직접 소비** | 라이브러리 없이 Streams를 직접 소비 | 중간(직접 구현 부담) | 직접 구현 | 직접 구현 |

FastAPI가 async 기반이라 **arq**가 궁합이 좋고, **Celery**는 기능이 가장 풍부하지만 무겁다.
**RQ**는 가장 단순하다. **Streams 직접 소비**는 의존성을 최소화하되 재시도·모니터링을
직접 만들어야 한다. 최종 선택은 팀의 운영 여건과 학습 목표에 따라 정한다.

## 3. 목표 아키텍처

### 3.1 구성요소와 책임 분리

- **FastAPI (API 서버)**
  - 요청 검증(진료기록·X-ray 존재), 캐시·중복 확인.
  - 예측이 필요하면 Redis에 **작업을 등록(enqueue)** 하고 **즉시 `202 Accepted`** 로 응답한다.
  - **모델을 로드하지 않는다.** (`load_models()`를 호출하지 않음 → API 프로세스가 가벼워짐)
- **Redis**
  - **작업 대기열**(List 또는 Streams).
  - **중복 방지 키** — 진행 중인 `record_id`를 표시해 같은 작업의 재등록을 막는다.
- **AI Worker (별도 프로세스)**
  - 시작 시 `load_models()`를 **1회** 호출해 5-fold 모델을 로드한다.
  - 큐에서 작업을 꺼내 `predict()`를 실행하고 결과를 DB(`ai_analysis_results`)에 저장한다.
  - **API와 독립적으로 프로세스 수를 조절**할 수 있어 추론 처리량을 따로 확장한다.

### 3.2 요청 흐름

1. 클라이언트가 `POST /medical-records/{record_id}/predictions` 요청.
2. API가 진료기록·X-ray 존재와 **캐시(`get_cached_result`)** 를 확인한다.
   - 이미 결과가 있으면 그 결과를 즉시 반환한다(현행 캐시 정책 유지).
3. 캐시가 없으면 **중복 방지 키**를 확인한다. 진행 중이 아니면 키를 설정하고
   Redis 큐에 `{record_id}` 작업을 등록한다.
4. API는 **`202 Accepted`** 와 함께 작업 식별자(예: `record_id` 또는 job id)를 반환한다.
5. **AI Worker**가 큐에서 작업을 꺼내(consume) `predict()`로 추론한다.
6. 워커가 결과를 DB에 저장하고, 진행 중 키를 해제한다.
7. 클라이언트는 결과를 **조회(GET /predictions)** 로 확인한다.

### 3.3 중복 추론 방지

큐 등록 **전에** `record_id` 기준 "진행 중" 키를 확인해, 이미 처리 중이면 **재등록하지 않는다.**
이는 현재의 사후 수습(추론을 다 하고 나서 `IntegrityError`로 정리)을
**사전 차단**(추론 자체를 한 번만 실행)으로 바꾸는 것이 핵심이다.
DB의 `UniqueConstraint`는 최종 안전장치로 그대로 유지한다.

### 3.4 결과 전달

- **기본: 폴링** — 클라이언트가 `GET /medical-records/{record_id}/predictions`를 주기적으로
  조회해 결과가 저장되었는지 확인한다. (기존 조회 API를 그대로 활용)
- **확장: SSE / WebSocket** — 완료 이벤트를 서버가 밀어주는 방식으로,
  폴링 주기·지연을 줄이고 싶을 때 도입을 검토한다.

### 3.5 실패·재시도

- 워커에서 추론이 예외로 실패하면 **재시도 횟수를 제한**하여 재처리한다.
- 재시도 한도를 초과하면 **실패 상태를 기록**해(예: 상태 필드/실패 로그) 클라이언트가
  "실패"를 인지할 수 있게 한다.
- 큐 방식으로 Streams(Consumer Group)를 쓰면 미확인(pending) 메시지 재분배로
  워커 장애 시 재처리가 수월하다.

## 4. 아키텍처 도식

![EDA 아키텍처](assets/day9-eda-architecture.png)

도식은 현재 구조(As-Is)와 목표 구조(To-Be)를 나란히 보여준다.

- **As-Is** — FastAPI 프로세스 안에서 `predict()`를 직접 실행(`anyio.to_thread`)한다.
  같은 `record_id` 동시 요청 시 중복 추론이 발생하고(→ `UniqueConstraint` 충돌을
  `IntegrityError`로 사후 수습), CPU 추론이 스레드를 점유해 다른 요청이 지연되거나
  3초 타임아웃(504)에 걸리며, 모델이 API 프로세스에 상주해 API 스케일이 모델 스케일과 묶인다.
- **To-Be** — FastAPI는 검증·캐시·중복 확인 후 Redis에 작업을 **enqueue**하고 즉시 **202**로 응답한다.
  Redis가 **작업 대기열**과 **중복 방지 키**(진행 중인 `record_id`)를 관리하고,
  **AI Worker**가 별도 프로세스에서 모델을 상주(`load_models()` 1회)시킨 뒤 큐를 소비해
  `predict()`로 추론하고 결과를 DB에 저장한다. 클라이언트는 `GET /predictions` **폴링**으로
  결과를 조회한다.

## 5. 도입 시 변경 지점 (구현은 이번 범위 밖)

- **`app/services/prediction_service.py`** — `run_prediction()`의 추론 호출
  (`anyio.to_thread.run_sync(predict, ...)` + 저장)이 **Redis 큐 등록(enqueue)** 으로 바뀐다.
  캐시·중복 확인은 남고, 실제 추론·저장은 워커로 이동한다.
- **`app/apis/predictions.py`** — `POST` 핸들러가 결과를 즉시 반환하는 대신
  **`202 Accepted`** 를 반환하도록 바뀐다.
- **AI Worker 진입점 신설** — 별도 프로세스에서 `load_models()` 후 큐를 소비하는
  워커 스크립트(예: `worker/` 하위)를 추가한다.
- **`app/main.py`** — API 프로세스의 `lifespan`에서 `load_models()` 호출을 제거한다
  (모델은 워커만 로드).
- **의존성/인프라** — Redis 클라이언트(및 선택 시 arq/celery/rq) 의존성과,
  `docker-compose.yml`에 `redis`·`worker` 서비스를 추가한다.
- **API 계약 변경 주의** — 현재 `POST /medical-records/{id}/predictions`는
  **`200/201`로 결과를 즉시 반환**한다. 이를 **`202 Accepted` + 폴링**으로 바꾸면
  **프론트엔드(record-detail 예측 버튼)도 함께 바뀌어야 한다.**
  즉, "요청 → 결과 즉시 표시"에서 "요청 → 접수 응답 → 결과 조회(폴링)"로 UX가 달라진다.
