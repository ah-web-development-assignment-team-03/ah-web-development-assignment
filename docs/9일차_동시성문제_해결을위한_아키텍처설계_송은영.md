# 9일차_동시성문제_해결을위한_아키텍처설계

AI 작업은 일반적인 API 요청보다 처리 시간이 길고 CPU, GPU 또는 외부 AI API와 같은 많은 자원을 사용할 수 있다. FastAPI가 요청을 받은 뒤 AI 작업이 끝날 때까지 직접 기다리는 구조에서는 요청이 증가할수록 응답이 느려지고 서버가 처리할 수 있는 요청 수도 감소한다.

FastAPI와 AI 작업을 분리하고 Redis를 작업 대기열로 사용하는 Event-Driven Architecture를 학습한다. 또한 여러 요청이 동시에 들어올 때 발생할 수 있는 동시성 문제와 이를 해결하기 위한 작업 큐, 재시도, ACK, 멱등성 설계를 정리한다.

---

### 기존 동기 처리 구조의 문제점

기존 동기 처리 구조는 다음과 같이 동작한다.

```
Client → FastAPI → AI 작업 실행 → 결과 저장 → 응답
```

이 구조에서는 다음 문제가 발생할 수 있다.

#### 1. 긴 응답 시간

FastAPI가 AI 작업이 끝날 때까지 연결을 유지해야 한다. AI 작업이 오래 걸리면 클라이언트, 프록시 또는 서버에서 timeout이 발생할 수 있다.

#### 2. 요청 처리 자원 점유

AI 연산이 API 서버와 같은 프로세스에서 실행되면 API 요청 처리에 사용해야 할 CPU, 메모리 및 이벤트 루프가 영향을 받을 수 있다.

#### 3. 순간적인 요청 증가

AI Worker가 처리할 수 있는 양보다 많은 요청이 한꺼번에 들어오면 모든 작업을 동시에 실행하려고 하면서 시스템 자원이 고갈될 수 있다.

#### 4. 장애 발생 시 작업 유실

메모리에만 등록한 백그라운드 작업은 FastAPI 서버가 재시작되거나 종료되면 유실될 수 있다.

#### 5. 중복 처리와 Race Condition

동일한 요청이 여러 번 전달되거나 Worker가 작업을 재처리하면 같은 결과가 중복 저장되거나 늦게 끝난 작업이 최신 결과를 덮어쓸 수 있다.

---

### Event-Driven Architecture

Event-Driven Architecture는 시스템 구성요소가 서로를 직접 호출해 모든 처리가 끝날 때까지 기다리지 않고, 이벤트 또는 메시지를 통해 느슨하게 연결되는 구조이다.

이 문서에서 각 구성요소의 역할은 다음과 같다.

| 구성요소 | 역할 |
| --- | --- |
| Client | AI 작업을 요청하고 `task_id`로 진행 상태를 조회한다. |
| FastAPI | 요청 검증, 작업 생성, 큐 등록, 상태 및 결과 조회를 담당한다. |
| Redis | FastAPI가 생성한 작업을 Worker가 가져갈 때까지 대기열에서 관리한다. |
| AI Worker | Redis에서 작업을 가져와 실제 AI 연산을 실행한다. |
| DB 또는 결과 저장소 | 작업 상태와 최종 결과를 저장한다. |
| Flower·로그·메트릭 | 큐와 Worker 상태, 실패 및 재시도를 관찰한다. |

이 구조에서는 FastAPI가 Producer, AI Worker가 Consumer, Redis가 Message Broker 역할을 한다.

---

### FastAPI 비동기 처리 방식 비교

FastAPI 애플리케이션에서 시간이 오래 걸리는 작업을 요청 처리 흐름과 분리하는 대표적인 방법은 `BackgroundTasks`, `asyncio.create_task()`, Celery의 세 가지로 나눌 수 있다. 
`BackgroundTasks`와 `asyncio.create_task()`는 FastAPI 프로세스 내부에서 실행되는 방식이고 Celery는 Redis와 같은 메시지 브로커와 별도의 Worker 프로세스를 사용하는 방식이라는 차이가 있다.

| 방식 | 실행 위치 | 추가 인프라 | 서버 재시작 시 작업 | 분산 처리 | 적합한 작업 |
| --- | --- | --- | --- | --- | --- |
| `BackgroundTasks` | FastAPI 프로세스 내부 | 필요 없음 | 작업이 유실될 수 있음 | 어려움 | 짧고 단순한 후처리 |
| `asyncio.create_task()` | FastAPI 이벤트 루프 | 필요 없음 | 작업이 유실될 수 있음 | 어려움 | 짧은 비동기 I/O 작업 |
| Celery | 별도의 Worker 프로세스 | Broker와 Worker 필요 | Broker 설정에 따라 미처리 작업 재전달 가능 | 가능 | AI 추론, 영상 처리 등 무거운 작업 |

### BackgroundTasks

`BackgroundTasks`는 HTTP 응답을 반환한 뒤 같은 애플리케이션 프로세스에서 작업을 실행한다.

장점:

- 구현이 단순하다.
- 별도의 메시지 브로커나 Worker가 필요하지 않다.
- 이메일 전송이나 간단한 로그 기록과 같은 짧은 작업에 적합하다.

한계:

- FastAPI 프로세스가 종료되면 진행 중인 작업이 유실될 수 있다.
- 무거운 AI 연산이 API 서버의 자원을 사용한다.
- 여러 서버와 Worker에 작업을 분산하기 어렵다.

### asyncio.create_task()

`asyncio.create_task()`는 코루틴을 현재 프로세스의 이벤트 루프에 등록한다.

장점:

- 작업을 즉시 실행할 수 있다.
- timeout, 취소 및 예외 처리를 직접 제어할 수 있다.

한계:

- FastAPI와 같은 프로세스에서 실행된다.
- 프로세스가 종료되면 작업이 유실될 수 있다.
- CPU 또는 GPU를 오래 사용하는 AI 작업을 분리하지 못한다.

### Redis Streams

Redis Streams는 지속적이고 순서가 있는 이벤트 로그를 제공하는 Redis 자료구조이다. 
Producer는 `XADD`로 이벤트를 추가하고 Consumer는 `XREADGROUP`으로 작업을 읽는다. 
이벤트가 Stream에 저장되므로 단순 Redis Pub/Sub과 달리 Consumer가 잠시 연결되지 않았더라도 이후 메시지를 읽거나 재처리할 수 있다.

주요 기능:

- `XADD`: Stream에 이벤트를 추가한다. `MAXLEN` 옵션을 사용하면 Stream이 무제한으로 증가하지 않도록 보관할 최대 길이를 설정할 수 있다.
- `XGROUP CREATE`: Consumer Group 생성
- `XREADGROUP`: Consumer Group을 통해 작업을 읽는다. Stream ID로 `>`를 사용하면 해당 그룹에 아직 전달되지 않은 새로운 메시지를 가져온다.
- `XACK`: 작업이 성공적으로 처리되었음을 Redis에 알리고 Consumer Group의 Pending Entries List에서 제거한다.
- `XPENDING`: Consumer에게 전달됐지만 아직 ACK되지 않은 작업을 확인한다.
- `XAUTOCLAIM`: Worker 장애 등으로 일정 시간 처리되지 않은 stale 메시지의 소유권을 정상 Consumer에게 이전한다.

Consumer Group을 사용하면 여러 Worker가 같은 Stream의 작업을 나누어 처리하여 부하를 분산할 수 있다. 처리 성공 후에만 `XACK`해야 하며 Worker 장애로 ACK되지 않은 작업은 다른 Worker가 다시 처리할 수 있다. 이러한 구조는 at-least-once 전달을 지원한다.

Redis Streams는 일반적으로 at-least-once 전달 방식이므로 같은 메시지가 한 번 이상 처리될 가능성이 있다. 따라서 Consumer가 동일한 작업을 다시 받아도 결과가 잘못되지 않도록 멱등성을 보장해야 한다.

간단한 서비스에서는 FastAPI 시작 시 `asyncio.create_task()`로 Redis Streams Consumer를 실행하여 별도의 Worker 프로세스 없이 구조를 단순화할 수 있다. 
그러나 이 방식은 Consumer가 FastAPI 프로세스의 수명과 자원을 공유하며 무거운 AI 작업이 API 처리에 영향을 줄 수 있다.
FastAPI와 AI Worker의 역할을 명확히 분리해야 하므로 Redis Streams를 사용하더라도 Consumer는 별도의 Worker 프로세스 또는 컨테이너로 구성한다.

### Celery & Redis

- Celery: 메일 발송, 비디오 처리, 데이터 가공, AI 모델 추론과 같이 시간이 오래 걸리는 작업을 백그라운드에서 실행할 수 있는 Python 분산 작업 큐 시스템이다.
- Redis를 Broker와 선택적인 Result Backend로 사용할 수 있다.

| 구성요소 | 역할 |
| --- | --- |
| Client | FastAPI에서 Task를 생성하여 Broker로 전송한다. |
| Broker | Redis와 같은 메시지 중개자로, Worker가 처리할 작업을 대기열에 보관한다. |
| Worker | Broker에서 작업을 가져와 실제 Task를 실행한다. |
| Result Backend | Redis 또는 DB 등에 Task 상태와 반환값을 저장한다. |
| Flower | Celery 작업과 Worker 상태를 모니터링한다. |

Celery를 사용하면 다음 기능을 비교적 쉽게 구성할 수 있다.

- Worker 프로세스 분리
- 여러 Worker를 이용한 병렬 처리
- 실패한 작업의 자동 재시도
- 작업 timeout
- 작업 상태 및 결과 관리
- 작업 연결과 순서 제어
- Flower를 이용한 모니터링

### Task 호출

등록된 Celery Task는 `delay()` 또는 `apply_async()`를 이용해 비동기로 큐에 추가할 수 있다.

```python
# 간단한 비동기 호출
result = run_ai_task.delay(task_id, input_path)

# 실행 옵션을 지정하는 호출
result = run_ai_task.apply_async(
    args=[task_id, input_path],
    countdown=5,
    queue="ai-tasks",
)
```

`delay()`는 `apply_async()`를 간단하게 호출하기 위한 단축 메서드이다. 실행할 큐, 지연 시간, 만료 시간 등 세부 옵션이 필요하면 `apply_async()`를 사용한다.

#### bind=True와 재시도

Task에 `bind=True`를 설정하면 첫 번째 인자로 Task 인스턴스인 `self`를 받아 현재 요청의 메타데이터를 확인하거나 `self.retry()`를 호출할 수 있다.

```python
@celery_app.task(bind=True, max_retries=3)
def run_ai_task(self, task_id: str, input_path: str):
    try:
        return execute_ai_model(task_id, input_path)
    except TemporaryAIError as exc:
        raise self.retry(exc=exc, countdown=30)
```

재시도는 네트워크 timeout, 외부 AI API의 일시적인 오류처럼 다시 시도하면 성공할 가능성이 있는 오류에만 적용한다.

#### Celery Beat

Celery Beat는 정해진 시간 또는 주기마다 Task를 Broker에 전달하는 스케줄러이다. 오래된 결과 정리, 실패 작업 점검, 통계 집계 등 주기적 작업에 활용할 수 있다. Beat는 스케줄링을 담당하며 실제 작업은 Celery Worker가 실행한다.

#### Celery Workflow

Celery Canvas를 이용하면 여러 Task의 실행 관계를 표현할 수 있다.

- `chain`: 이전 Task의 결과를 다음 Task에 전달하며 순차 실행
- `group`: 여러 Task를 병렬 실행
- `chord`: 여러 병렬 Task가 모두 끝난 뒤 Callback 실행

예를 들어 파일 변환, AI 추론, 결과 요약이 순서대로 실행되어야 한다면 `chain`을 사용할 수 있다.

```
파일 변환 → AI 추론 → 결과 요약 → 결과 저장
```

#### Worker 동시 실행 수

Celery Worker의 동시 실행 수는 일반적인 CPU 작업에서는 사용 가능한 CPU 코어 수를 출발점으로 검토할 수 있다. 그러나 GPU 추론, 메모리 사용량이 큰 모델, 외부 AI API 호출 작업은 CPU 코어 수만으로 결정하지 않고 GPU 메모리, 프로세스별 메모리, API Rate Limit과 실제 부하 테스트 결과를 기준으로 조정해야 한다.

### Redis Streams와 Celery + Redis 비교

| 구분 | Redis Streams 직접 사용 | Celery + Redis |
| --- | --- | --- |
| 작업 발행 | `XADD` 직접 호출 | Celery Task 호출 |
| 작업 소비 | `XREADGROUP` Consumer 직접 구현 | Celery Worker가 처리 |
| ACK | `XACK` 직접 구현 | Celery 설정과 Worker가 관리 |
| 장애 복구 | Pending, `XAUTOCLAIM` 직접 구현 | 재전달 및 retry 설정 활용 |
| 재시도 | 애플리케이션에서 직접 구현 | Celery retry 기능 활용 |
| 모니터링 | Redis 명령이나 별도 도구 필요 | Flower 사용 가능 |
| 구현 난이도 | 세부 제어가 가능하지만 구현량이 많음 | 설정이 필요하지만 작업 큐 기능이 풍부함 |
| 적합한 경우 | 이벤트 로그, 재생, Consumer 제어가 중요할 때 | AI 작업과 백그라운드 Job 처리가 중심일 때 |

### 꼭 알아야 할 핵심 코드

다음 코드는 전체 애플리케이션 구현이 아니라 FastAPI, Redis, Celery가 어떤 방식으로 연결되는지 이해하기 위한 핵심 예시이다.

#### Celery와 Redis 연결

```python
from celery import Celery

celery_app = Celery(
    "ai_tasks",
    broker="redis://redis:6379/0",
    backend="redis://redis:6379/1",
)

celery_app.conf.update(
    task_track_started=True,
    task_acks_late=True,
    worker_prefetch_multiplier=1,
    broker_transport_options={"visibility_timeout": 3600},
)
```

핵심 설정:

- `broker`: FastAPI가 생성한 Task를 Redis 작업 큐에 전달한다.
- `backend`: Celery Task 상태와 반환값을 Redis에 저장한다.
- `task_track_started`: `STARTED` 상태를 추적할 수 있게 한다.
- `task_acks_late`: Task 실행이 끝난 뒤 ACK하도록 한다.
- `worker_prefetch_multiplier=1`: 한 Worker가 실행하기 전에 많은 작업을 미리 가져가는 현상을 줄인다.
- `visibility_timeout`: 제한 시간 동안 ACK되지 않은 작업을 다시 전달할 수 있게 한다. 실제 값은 AI 작업의 최대 실행 시간을 고려해야 한다.

Broker와 Result Backend는 같은 Redis 서버를 사용할 수 있지만 예시처럼 DB 번호를 분리하면 작업 메시지와 결과 키를 구분하기 쉽다. 중요한 비즈니스 상태와 최종 결과는 Redis에만 의존하지 않고 애플리케이션 DB에도 저장하는 것이 좋다.

#### FastAPI에서 작업 발행

```python
from uuid import uuid4
from fastapi import FastAPI, Header, status

app = FastAPI()

@app.post("/ai-tasks", status_code=status.HTTP_202_ACCEPTED)
async def create_ai_task(
    request: AiTaskRequest,
    idempotency_key: str = Header(alias="Idempotency-Key"),
):
    existing_job = find_job_by_idempotency_key(idempotency_key)
    if existing_job:
        return {
            "task_id": existing_job.task_id,
            "status": existing_job.status,
        }

    task_id = str(uuid4())
    create_job(
        task_id=task_id,
        idempotency_key=idempotency_key,
        status="QUEUED",
    )

    run_ai_task.apply_async(
        args=[task_id, request.model_dump()],
        task_id=task_id,
        queue="ai-tasks",
    )

    return {
        "task_id": task_id,
        "status": "QUEUED",
        "status_url": f"/ai-tasks/{task_id}",
    }
```

이 Endpoint에서 FastAPI는 AI 연산을 직접 실행하지 않는다. 작업 정보만 저장하고 Celery Task를 Redis Broker에 등록한 뒤 `202 Accepted`를 반환한다.

`Idempotency-Key`로 기존 작업을 먼저 조회하면 클라이언트가 같은 요청을 다시 전송했을 때 새로운 Task를 중복 생성하는 문제를 줄일 수 있다. 실제 운영 환경에서는 작업 DB 저장에는 성공했지만 Redis 발행에 실패하는 경우도 고려하여 Transactional Outbox 같은 패턴을 검토할 수 있다.

#### Celery AI Worker의 재시도와 멱등성

```python
@celery_app.task(bind=True, max_retries=3)
def run_ai_task(self, task_id: str, payload: dict):
    job = get_job(task_id)

    # 재전달된 작업이 이미 완료됐다면 다시 실행하지 않는다.
    if job.status == "SUCCESS":
        return job.result

    update_job_status(task_id, "PROCESSING")

    try:
        result = execute_ai_model(payload)
        save_result_once(task_id, result)  # task_id를 Unique Key로 사용
        update_job_status(task_id, "SUCCESS")
        return result

    except TemporaryAIError as exc:
        update_job_status(task_id, "RETRYING")
        raise self.retry(exc=exc, countdown=30)

    except Exception:
        update_job_status(task_id, "FAILURE")
        raise
```

이 코드에서 꼭 확인해야 할 부분은 다음과 같다.

1. `task_id`로 기존 성공 여부를 확인하여 중복 실행을 방지한다.
2. 결과를 `task_id` Unique Key 기준으로 저장하여 중복 결과 생성을 막는다.
3. 일시적인 오류만 `self.retry()`로 재시도한다.
4. 처리되지 않은 예외는 다시 발생시켜 Celery가 Task를 성공으로 판단하지 않게 한다.
5. `task_acks_late=True`이면 Task가 정상적으로 반환된 뒤 ACK된다.

실제 환경에서는 여러 Worker가 동시에 같은 작업을 실행할 가능성까지 고려하여 상태 변경 시 조건부 UPDATE를 사용하는 것이 좋다.

```sql
UPDATE ai_jobs
SET status = 'PROCESSING'
WHERE task_id = :task_id
  AND status IN ('QUEUED', 'RETRYING');
```

변경된 행이 없으면 다른 Worker가 이미 처리 중이거나 완료한 작업으로 판단할 수 있다.

#### 작업 상태 조회

```python
from fastapi import HTTPException

@app.get("/ai-tasks/{task_id}")
async def get_ai_task(task_id: str):
    job = get_job(task_id)
    if job is None:
        raise HTTPException(status_code=404, detail="Task not found")

    return {
        "task_id": job.task_id,
        "status": job.status,
        "result": job.result if job.status == "SUCCESS" else None,
        "error": job.error if job.status == "FAILURE" else None,
    }
```

클라이언트는 작업 등록 응답으로 받은 `task_id`를 이용해 진행 상태를 조회한다. Celery Result Backend의 상태를 직접 노출하기보다 애플리케이션 DB의 상태를 반환하면 사용자에게 필요한 비즈니스 상태를 더 명확하게 표현할 수 있다.

### Redis Streams를 선택할 때 알아야 할 코드

#### Producer: 이벤트 발행

```python
from redis.asyncio import Redis

redis = Redis.from_url("redis://redis:6379/0", decode_responses=True)

async def publish_ai_task(task_id: str, input_path: str) -> str:
    message_id = await redis.xadd(
        "ai-tasks",
        {
            "task_id": task_id,
            "input_path": input_path,
        },
        maxlen=10_000,
        approximate=True,
    )
    return message_id
```

`XADD`는 이벤트를 Stream에 추가한다. `maxlen`은 Stream이 계속 증가하여 Redis 메모리를 고갈시키는 문제를 방지하기 위한 보관 정책이다.

#### Consumer Group 생성

```python
from redis.exceptions import ResponseError

async def ensure_consumer_group() -> None:
    try:
        await redis.xgroup_create(
            name="ai-tasks",
            groupname="ai-workers",
            id="0",
            mkstream=True,
        )
    except ResponseError as exc:
        if "BUSYGROUP" not in str(exc):
            raise
```

Consumer Group은 한 번만 생성한다. 이미 존재한다는 `BUSYGROUP` 오류만 무시하고 다른 Redis 오류는 숨기지 않아야 한다.

#### Consumer: 작업 처리와 ACK

```python
async def consume_ai_tasks() -> None:
    while True:
        streams = await redis.xreadgroup(
            groupname="ai-workers",
            consumername="worker-1",
            streams={"ai-tasks": ">"},
            count=1,
            block=5_000,
        )

        for _, messages in streams:
            for message_id, payload in messages:
                try:
                    await process_ai_task(payload)
                    await redis.xack(
                        "ai-tasks",
                        "ai-workers",
                        message_id,
                    )
                except Exception:
                    # ACK하지 않으면 Pending 상태로 남아 복구할 수 있다.
                    logger.exception("AI task processing failed")
```

`streams={"ai-tasks": ">"}`는 Consumer Group에 아직 전달되지 않은 새로운 메시지를 읽는다는 의미이다. `XACK`는 AI 처리와 결과 저장이 모두 성공한 뒤 호출해야 한다.

#### 방치된 Pending 작업 복구

```python
async def reclaim_stale_tasks() -> None:
    next_id, messages, _ = await redis.xautoclaim(
        name="ai-tasks",
        groupname="ai-workers",
        consumername="worker-recovery",
        min_idle_time=60_000,
        start_id="0-0",
        count=10,
    )

    for message_id, payload in messages:
        await process_ai_task(payload)
        await redis.xack("ai-tasks", "ai-workers", message_id)
```

`XAUTOCLAIM`은 지정한 시간 동안 ACK되지 않은 메시지를 정상 Consumer가 인계하도록 한다. 재처리 과정에서도 중복 실행이 발생할 수 있으므로 Celery 방식과 마찬가지로 `task_id` 기반 멱등성이 필요하다.

## 최종 아키텍처

최종 구조는 다음과 같다.

```
Client
  │
  │ 1. POST /ai-tasks
  ▼
FastAPI API Server
  ├─ 요청 데이터 검증
  ├─ task_id 및 idempotency_key 생성·검사
  ├─ 작업 상태를 QUEUED로 저장
  ├─ Redis Broker에 작업 등록
  └─ 202 Accepted와 task_id 반환
                    │
                    │ 2. 작업 메시지
                    ▼
              Redis Broker
              작업 대기열 관리
                    │
                    │ 3. 작업 소비
                    ▼
             Celery AI Worker × N
              ├─ 상태를 PROCESSING으로 변경
              ├─ AI 모델 또는 외부 AI API 실행
              ├─ 결과 저장
              ├─ SUCCESS 또는 FAILURE 기록
              └─ 성공 후 작업 ACK
                    │
                    ▼
              DB / 결과 저장소

Client
  │
  │ GET /ai-tasks/{task_id}
  ▼
FastAPI → DB 또는 Result Backend → 상태와 결과 반환
```

### FastAPI의 책임

- HTTP 요청과 인증 처리
- 요청 데이터 검증
- `task_id` 생성
- 중복 요청 검사
- 작업 상태 생성
- Redis Broker에 작업 등록
- `202 Accepted` 응답
- 작업 상태 및 결과 조회 API 제공

FastAPI는 AI 모델을 직접 실행하지 않는다.

### AI Worker의 책임

- Redis Broker에서 작업 소비
- 작업 상태를 `PROCESSING`으로 변경
- AI 모델 또는 외부 AI API 실행
- 성공 결과 저장
- 실패 원인 기록
- 재시도 여부 결정
- 작업 완료 후 ACK

AI Worker는 HTTP 요청과 응답을 직접 처리하지 않는다.

### Redis의 책임

- FastAPI와 AI Worker 사이의 작업 전달
- Worker가 처리할 수 있을 때까지 작업 대기
- 여러 Worker에 작업 분배
- 완료되지 않은 작업의 재전달 지원

Redis는 영구적인 비즈니스 데이터 저장소와 역할이 다르므로, 중요한 작업 상태와 최종 결과는 DB에 별도로 저장하는 것이 안전하다.

### API 및 작업 상태 설계

#### 작업 등록

```python
POST /ai-tasks
Idempotency-Key: request-unique-key
```

```python
# 예시 응답:
HTTP/1.1 202 Accepted

{
  "task_id": "01JXXXXXXXXXXXXXXX",
  "status": "QUEUED",
  "status_url": "/ai-tasks/01JXXXXXXXXXXXXXXX"
}
```

#### 작업 조회

```
GET /ai-tasks/{task_id}
```

```json
# 처리 중 응답:

{
  "task_id": "01JXXXXXXXXXXXXXXX",
  "status": "PROCESSING"
}
```

```json
# 완료 응답:

{
  "task_id": "01JXXXXXXXXXXXXXXX",
  "status": "SUCCESS",
  "result": {
    "summary": "AI 작업 결과"
  }
}
```

#### 작업 상태

```
QUEUED → PROCESSING → SUCCESS
                    └→ RETRYING → PROCESSING
                    └→ FAILURE
```

허용된 상태 전이만 수행하도록 하면 여러 Worker가 동시에 상태를 변경하면서 발생하는 Race Condition을 줄일 수 있다.

### 동시성 문제와 해결 방법

| 동시성 문제 | 발생 상황 | 해결 방법 |
| --- | --- | --- |
| 요청 폭주 | Worker 처리량보다 많은 요청이 동시에 발생 | Redis 큐에 작업을 적재하고 Worker 처리량만큼 소비 |
| API 서버 자원 점유 | FastAPI가 AI 연산을 직접 수행 | FastAPI와 AI Worker 프로세스 분리 |
| 동일 요청 중복 등록 | 클라이언트 timeout 후 같은 요청을 재전송 | `Idempotency-Key` 저장 및 기존 `task_id` 반환 |
| 작업 중복 실행 | ACK 전 Worker 종료 또는 timeout으로 작업 재전달 | Task를 멱등하게 구현하고 `task_id` 기준 중복 검사 |
| 결과 덮어쓰기 | 여러 Worker가 같은 작업 결과를 저장 | 조건부 UPDATE 또는 상태 버전을 이용한 원자적 상태 전이 |
| Worker 장애 | Worker가 처리 중 종료 | 성공 후 ACK, 처리되지 않은 작업 재전달 |
| 계속 실패하는 작업 | 잘못된 데이터 또는 외부 API 장애 | 최대 재시도 횟수, 지수 Backoff, Dead Letter Queue |
| AI API 호출량 초과 | Worker가 외부 API를 동시에 과도하게 호출 | Worker concurrency, rate limit, semaphore 설정 |
| 큐 적체 | 들어오는 작업이 처리량보다 지속적으로 많음 | 큐 길이 모니터링, Worker 수평 확장, 요청 제한 |

### 멱등성

멱등성이란 같은 작업을 한 번 실행하거나 여러 번 실행해도 최종 결과가 같도록 만드는 성질이다.

권장 방법:

1. 모든 작업에 고유한 `task_id`를 부여한다.
2. 클라이언트 요청에는 `Idempotency-Key`를 사용한다.
3. 이미 `SUCCESS` 상태인 작업은 다시 실행하지 않는다.
4. 결과 저장 시 `task_id`에 Unique Constraint를 적용한다.
5. 외부 시스템 변경 작업에는 별도의 처리 완료 키를 저장한다.

### ACK 시점

작업을 큐에서 가져온 즉시 완료 처리하지 않고 다음 작업이 모두 성공한 뒤 ACK한다.

```
작업 소비
→ AI 처리
→ 결과 저장
→ 상태 SUCCESS 기록
→ ACK
```

결과를 저장하기 전에 ACK하면 Worker 장애 시 작업과 결과가 모두 유실될 수 있다.

### 재시도

일시적인 외부 AI API 장애나 네트워크 오류는 재시도할 수 있지만 잘못된 요청 데이터와 같은 영구 오류는 즉시 실패 처리하는 것이 좋다.

예시 정책:

- 최대 재시도: 3회
- 재시도 간격: 지수 Backoff
- 일시적 오류: timeout, 429, 일부 5xx 응답
- 영구 오류: 잘못된 입력, 인증 실패, 지원하지 않는 파일
- 최대 재시도 초과: `FAILURE` 또는 Dead Letter Queue 이동

### Celery Visibility Timeout

Redis Broker를 사용하는 Celery에서는 Worker가 제한 시간 안에 작업을 ACK하지 않으면 다른 Worker에 작업이 다시 전달될 수 있다. AI 작업의 최대 실행 시간이 Visibility Timeout보다 길면 동일 작업이 중복 실행될 수 있으므로 다음을 함께 고려해야 한다.

- AI 작업의 예상 최대 처리 시간 측정
- 작업별 soft time limit과 hard time limit 설정
- 적절한 Visibility Timeout 설정
- `task_acks_late` 사용 여부 검토
- Worker 종료 시 graceful shutdown 적용
- 작업 자체의 멱등성 보장

### 확장 및 모니터링

#### Worker 확장

큐에 쌓인 작업 수가 증가하면 FastAPI 인스턴스와 독립적으로 AI Worker 수를 늘릴 수 있다.

```
Redis Broker
  ├─ AI Worker 1
  ├─ AI Worker 2
  └─ AI Worker 3
```

단, Worker 수는 CPU, GPU, 메모리, 외부 AI API Rate Limit을 고려하여 제한해야 한다.

#### 모니터링 대상

- Redis 큐 길이
- 가장 오래 대기 중인 작업의 시간
- `QUEUED`, `PROCESSING`, `SUCCESS`, `FAILURE` 작업 수
- 평균 및 최대 작업 처리 시간
- 재시도 횟수
- 실패율
- Worker별 처리량
- Worker heartbeat
- 외부 AI API latency와 오류율

#### Celery 작업 상태

Celery Result Backend를 설정하면 Task의 진행 상태와 결과를 조회할 수 있다.

| 상태 | 의미 |
| --- | --- |
| `PENDING` | 결과가 아직 없거나 Task가 실행 대기 중이다. 존재하지 않는 Task ID도 `PENDING`으로 보일 수 있으므로 별도의 작업 DB와 함께 확인하는 것이 안전하다. |
| `STARTED` | Worker가 Task 실행을 시작했다. `task_track_started` 설정을 활성화해야 추적할 수 있다. |
| `RETRY` | Task 실행 중 오류가 발생하여 재시도를 기다리고 있다. |
| `SUCCESS` | Task 실행이 성공적으로 완료되었다. |
| `FAILURE` | Task 실행이 최종적으로 실패했다. |
| `REVOKED` | Task 실행이 취소되었다. |

Celery 상태만 사용하면 비즈니스 관점의 세부 상태를 충분히 표현하기 어려울 수 있다. 따라서 사용자에게 보여주는 `QUEUED`, `PROCESSING`, `RETRYING`, `SUCCESS`, `FAILURE` 상태는 애플리케이션 DB에도 저장하고 Celery 상태와 연결하는 것이 좋다.

#### Flower

Flower는 Celery를 위한 웹 기반 모니터링 도구이다. 기본적으로 `5555` 포트를 사용하며 다음 정보를 확인할 수 있다.

- 실행 중인 Worker와 heartbeat
- Task의 성공, 실패, 재시도 상태
- Task 실행 시간과 인자
- Worker별 처리 Task 수
- 활성 Task와 예약된 Task
- Task 취소 및 Worker 관리

```bash
celery -A app.celery_app flower --port=5555
```

Flower는 개발 및 운영 중 Task 상태를 빠르게 확인하는 데 유용하지만 장기간의 로그와 메트릭 저장소를 완전히 대체하지는 않는다. 운영 환경에서는 구조화된 애플리케이션 로그, Redis와 Worker 메트릭, 알림 시스템을 함께 사용하는 것이 좋다.
