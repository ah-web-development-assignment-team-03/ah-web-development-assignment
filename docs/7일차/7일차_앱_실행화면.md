# 7일차 - 앱 실행화면

## 로그인 (`POST /api/v1/auth/login`)

`/login` 페이지에서 이메일·비밀번호를 입력해 로그인하는 화면입니다.

<!-- 사진 URL을 아래에 넣어주세요 -->
<img src="assets/day_07_login.png" width="600" alt="로그인 화면">

- 폼 제출 시 `apis.login(email, password)` → `POST /auth/login` 호출.
- 성공 시 응답의 `access_token`을 `localStorage`에 저장하고 `checkAuth()`로 사용자 정보를 불러온 뒤 `/patients`로 이동.
  - 권한이 `pending`(승인 대기) 상태이면 `/`(홈)으로 이동.
- 로그인 실패(이메일·비밀번호 불일치) 시 폼 하단에 "아이디 또는 비밀번호를 확인해주세요." 인라인 에러 메시지 표시.
- Refresh Token은 HTTP-only Cookie로 발급되어 JS에서 직접 접근 불가(NFR-USER-001).

## 로그아웃 (`POST /api/v1/auth/logout`)

네비게이션 바의 "로그아웃" 링크를 눌러 세션을 종료하는 화면입니다.

<!-- 사진 URL을 아래에 넣어주세요 -->
<img src="assets/day_07_logout1.png" width="600" alt="로그아웃 후 로그인 페이지 이동">
<img src="assets/day_07_logout2.png" width="600" alt="로그아웃 후 로그인 페이지 이동">

- `apis.logout()` → `POST /auth/logout` 호출.
- 성공·실패 모두 클라이언트 세션(`state.token`, `localStorage`의 `token`·`isLoggedIn`)을 즉시 초기화하고 `/login`으로 이동.
  - 서버 오류가 발생해도 클라이언트 측 세션은 반드시 정리됨(로그아웃 안전성 보장).

## 회원가입 (`POST /api/v1/users`)

`/signup` 페이지에서 이메일·이름·부서·성별·전화번호·비밀번호를 입력해 계정을 생성하는 화면입니다.

<!-- 사진 URL을 아래에 넣어주세요 -->
<img src="assets/day_07_register.png" width="600" alt="회원가입 화면">

- 폼 제출 시 `apis.signup(userData)` → `POST /users` 호출.
  - 전화번호는 숫자만 추출(`replace(/[^\d]/g, '')`)해 전송.
- 성공 시 "회원가입이 완료되었습니다. 로그인해주세요." 알림 후 `/login`으로 이동.
- 실패 케이스 처리:
  - **400** (비밀번호 정책 위반): "대소문자, 특수문자, 숫자를 각 1개씩 포함한 8자리 이상이어야 합니다." 안내.
  - **500**: "잠시 후 다시시도해주세요." 안내.
- 가입 직후 권한은 `pending` 상태이며, 관리자 승인 후 서비스 이용 가능.

## 홈 로그인 상태 확인 (`GET /api/v1/users/me`)

로그인 후 `/` 홈 화면에 접속해 현재 사용자 정보와 권한에 맞는 동작이 표시되는지 확인한 화면입니다.

<img src="assets/day7-b-home-get-me.png" width="600" alt="로그인 사용자 홈 화면">

- 앱 진입 시 `checkAuth()`가 `apis.getMe()`를 호출해 사용자 정보를 `state.user`에 저장.
- 로그인 사용자의 이름과 부서를 네비게이션 바에 표시.
- 권한이 `staff` 또는 `admin`이면 "환자 목록 보기" 버튼을 표시.
- 권한이 `pending`이면 관리자 승인 대기 메시지를 표시.

## 마이페이지 내 정보 조회 (`GET /api/v1/users/me`)

`/my-page`에서 로그인 사용자의 기본 정보와 수정 폼의 초기값을 확인한 화면입니다.

<img src="assets/day7-b-my-page-get-me.png" width="600" alt="마이페이지 내 정보 조회">

- 이메일, 이름, 부서, 성별, 전화번호, 권한을 화면에 표시.
- 조회한 사용자 정보로 부서와 전화번호 수정 폼의 초기값을 설정.
- 비밀번호와 비밀번호 해시는 응답 및 화면에 노출하지 않음.

## 마이페이지 내 정보 수정 (`PATCH /api/v1/users/me`)

마이페이지에서 부서와 전화번호를 수정하고 성공 알림을 확인한 화면입니다.

<img src="assets/day7-b-update-me.png" width="600" alt="내 정보 수정 성공">

- `apis.updateMe({ department, phone_number })`로 수정 요청.
- 전화번호는 하이픈을 제거하고 숫자만 전송.
- 성공 응답은 `200 OK`.
- 수정 성공 후 `checkAuth()`를 다시 호출해 `state.user`, 네비게이션 바, 마이페이지 내용을 갱신.

## 마이페이지 비밀번호 변경 (`PATCH /api/v1/users/me/password`)

현재 비밀번호와 새 비밀번호를 입력해 비밀번호를 변경한 화면입니다.

<img src="assets/day7-b-update-password.png" width="600" alt="비밀번호 변경 성공">

- `current_password`, `new_password`를 요청 본문으로 전송.
- 성공 응답은 `200 OK`.
- 성공 후 입력 폼을 초기화하고 완료 알림을 표시.
- 새 비밀번호는 대문자·소문자·숫자·특수문자를 포함한 8자리 이상 정책을 적용.

---

## 마이페이지 회원 탈퇴 (`DELETE /api/v1/users/me`)

현재 비밀번호 확인과 사용자 확인 절차를 거쳐 회원 탈퇴를 완료한 화면입니다.

<img src="assets/day7-b-delete-me.png" width="600" alt="회원 탈퇴 성공">

- 현재 비밀번호를 `{ current_password }` 요청 본문으로 전달.
- 브라우저 확인창에서 탈퇴 의사를 한 번 더 확인.
- 성공 응답은 `204 No Content`.
- 성공 후 Access Token과 로그인 상태를 제거하고 `/login`으로 이동.

## 진료 상세 (record-detail) — `/medical-records/1`

> record-detail·admin-users 담당(Stage7 E). 관련 이슈 #62 / PR #63. 로컬 서버(`fastapi run`, `:8000`)에 시드 데이터를 넣고 관리자 계정으로 접속해 캡처했다.

![진료 상세 화면](assets/day7-e-record-detail.png)

- **표시되는 정보**: 진료기록 ID, 차트번호(`CHART-2026-0001`), 증상, 등록일.
- **AI 폐렴 예측 결과표**: `GET /medical-records/{id}/predictions` 응답을 표로 렌더.
  - 예측 경로를 `…/predict` → `…/predictions` 로 정정.
  - 응답이 배열이 아니라 `{items, page, size, total}` 이므로 `items` 를 순회.
  - 수행 일시 필드는 `created_at` 이 아니라 서버 필드명 `predicted_at` 을 사용.
  - 캡처 예시: `Positive`, Confidence `84.3%`, 사용 모델 `v7_densenet121_5fold`.
- **X-Ray 이미지는 표시되지 않음(의도된 현재 한계)**:
  - `GET /medical-records/{id}` 응답의 `xray_image_url` 이 **항상 `null`** 이다.
    (백엔드가 "X-Ray 조회 정책 확정 전까지 `None` 반환" 으로 구현 — 목록/상세에 이미지 URL 미포함)
  - 프론트는 `record.xray_image_url` 을 `<img src>` 에 넣으므로 값이 `null` 이면 위 캡처처럼 이미지가 깨져 보인다.
  - 이는 백엔드 정책(은영님 파트) 확정 후 상세 응답에 `xray_image_url` 을 채우면 해결된다. 프론트 수정 사항 아님.

## 회원 관리 (admin-users) — `/admin/users` (관리자 전용)

![회원 관리 화면](assets/day7-e-admin-users.png)

- **회원 목록**: `GET /admin/users` 응답이 `{items, …}` 이므로 `items` 를 순회. 6명(다양한 부서·활성/비활성) 표시.
- **부서 필터**: option `value` 를 서버 `Department` enum(`DEV`/`MEDICAL`/`RESEARCH`)으로 맞춤.
  - (리뷰 반영) 기존 `developer`/`medical team`/`researcher` 값은 서버 enum과 불일치해 부서 필터 시 **422** 가 났음.
- **검색**: 쿼리 파라미터명을 `query` → `search` 로 정정(서버 파라미터명 일치). 이전엔 서버가 무시해 이름/이메일 검색이 동작하지 않았음.
- **권한(role) 드롭다운**: 맨 위 `권한 변경` placeholder 로 표시.
  - (리뷰 반영) `GET /admin/users` 목록 응답에는 `role` 이 **포함되지 않는다**(REQ-USER-004 스펙). 따라서 각 회원의 현재 권한을 드롭다운에 **미리 선택(preselect)할 수 없음**.
  - "현재 권한 표시"가 아니라 "권한을 변경" 하는 UI 로 바꾸고, placeholder(빈값) 선택 시 빈 role 전송을 막는 가드를 추가.
  - 권한 변경 동작 자체(`PATCH /admin/users/{id}/role`, 소문자 value → 대문자 enum 전송)는 정상.

### 검증 요약 (record-detail · admin-users)
- 4개 API E2E 200 확인: `GET/POST …/predictions`, `GET /admin/users`, `PATCH /admin/users/{id}/role`.
- 부서 필터: `?department=DEV` → 200(필터됨), 기존 `?department=developer` → 422(버그 재현).
- 검색: `?search=` 정상 필터, 기존 `?query=` → 서버 무시(버그 재현).
- 변경 범위: 프론트(`static/`)만. 백엔드(`app/`)·DB 무변경.
