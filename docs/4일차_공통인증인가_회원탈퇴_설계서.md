# 공통 인증·인가 및 회원 탈퇴 기능 설계서

## 1. 문서 개요

### 1.1 작성 목적

본 문서는 사용자 요구사항 정의서에서 Person 5에게 할당된 공통 인증·인가, 회원 탈퇴 및 사용자 API 성능 검증 기능의 구현 방향을 정의한다.

본 설계서는 내부 처리 방식과 컴포넌트 간 책임을 설명한다. HTTP 요청·응답 필드와 예시는 설계 검토가 끝난 후 별도의 API 명세서에서 정의한다.

## 2. 설계 범위

### 2.1 포함 범위

- 요청의 Bearer Access Token 추출
- Person 2가 제공하는 `decode_token()` 호출
- 토큰에서 반환된 `user_id`를 이용한 현재 사용자 조회
- 존재하지 않거나 비활성화된 사용자 접근 차단
- 공통 인증 Dependency 제공
- 역할 기반 접근 제어 Dependency 제공
- 현재 비밀번호 재확인 후 회원 하드 삭제
- 회원 삭제 시 해당 회원이 업로드한 `xray_images` 데이터 자동 삭제
- 사용자 API의 요청별 응답시간 검증

### 2.2 제외 범위

- Access Token 및 Refresh Token 생성
- JWT 서명과 만료시간 검증 로직 자체
- Refresh Token 재발급 및 HttpOnly Cookie 처리
- 로그아웃 처리
- X-ray 파일이 외부 스토리지에 저장되는 경우 실제 파일 삭제
- 고부하·대규모 동시 사용자 부하 테스트

외부 스토리지의 실제 이미지 파일 삭제는 현재 요구사항에서 Database 데이터 삭제만 명시하고 있으므로 본 설계의 범위에서 제외한다. 추후 저장소 정책이 확정되면 별도 요구사항으로 추가한다.

## 3. 시스템 구성 및 책임

```text
클라이언트 요청
    │
    ├─ Authorization: Bearer <access_token>
    │
    ▼
공통 인증 Dependency
    │
    ├─ 토큰 추출
    ├─ decode_token(token) 호출
    ├─ user_id 확인
    └─ users 테이블 조회
    │
    ▼
현재 사용자 객체
    │
    ├─ 역할 기반 인가 Dependency
    └─ 회원 탈퇴 API
```

공통 인증 Dependency는 토큰을 직접 생성하거나 JWT 내부 규칙을 다시 구현하지 않는다. 토큰 해석은 Person 2의 `decode_token()`을 단일 진입점으로 사용한다.

## 4. 공통 인증 Dependency 설계

### 4.1 목적

인증이 필요한 API에서 동일한 토큰 검증 및 사용자 조회 코드를 반복하지 않도록 현재 로그인 사용자를 반환하는 공통 Dependency를 제공한다.

예상 함수명은 `get_current_user()`이며 실제 모듈 위치와 함수 시그니처는 팀의 디렉터리 구조 및 `decode_token()` 인터페이스를 확인한 후 확정한다.

### 4.2 처리 절차

1. 요청의 `Authorization` 헤더에서 Bearer Token을 추출한다.
2. 토큰이 없거나 Bearer 형식이 아니면 `401 Unauthorized`를 반환한다.
3. Person 2가 제공하는 `decode_token()`에 토큰을 전달한다.
4. 토큰이 만료·위조·손상되었으면 `401 Unauthorized`를 반환한다.
5. 해석된 결과에서 `user_id`를 가져온다.
6. `user_id`가 없거나 올바른 형식이 아니면 `401 Unauthorized`를 반환한다.
7. 데이터베이스에서 사용자를 조회한다.
8. 사용자가 존재하지 않으면 `404 Not Found`를 반환한다.
9. 사용자의 `is_active`가 `False`이면 접근을 거부한다.
10. 모든 검증이 끝나면 현재 사용자 객체를 API Handler에 전달한다.

### 4.3 `decode_token()` 연동 계약

다음 항목은 Person 2의 구현 공유 후 확정한다.

- 함수의 매개변수와 반환 자료형
- 반환값이 전체 Payload인지 `user_id` 단일 값인지 여부
- `user_id`의 자료형
- 만료 토큰과 유효하지 않은 토큰의 예외 형식
- Access Token과 Refresh Token을 구분하는 방법
- 실패 시 예외를 발생시키는지 `None`을 반환하는지 여부

공통 인증 Dependency에서는 `decode_token()`의 예외를 외부에 그대로 노출하지 않고 프로젝트의 공통 HTTP 오류 형식으로 변환한다.

## 5. 역할 기반 인가 설계

### 5.1 역할 정의

| 역할 | 접근 범위 |
| --- | --- |
| `PENDING` | 마이페이지 외 서비스 접근 제한 |
| `STAFF` | 흉부 X-ray 관련 읽기·쓰기·수정 기능 사용 가능 |
| `ADMIN` | 시스템의 모든 데이터와 관리자 기능 접근 가능 |

### 5.2 처리 절차

1. `get_current_user()`를 통해 인증된 사용자를 전달받는다.
2. API가 허용하는 역할 목록과 현재 사용자의 역할을 비교한다.
3. 허용된 역할이면 요청 처리를 계속한다.
4. 인증은 되었지만 역할이 허용되지 않으면 `403 Forbidden`을 반환한다.

역할 검사는 API Handler 내부에서 반복하지 않고 `require_roles()` 또는 역할별 Dependency로 제공한다. 최종 함수 형태는 실제 적용 대상 API와 팀 코딩 규칙을 확인한 후 결정한다.

## 6. 회원 탈퇴 설계

### 6.1 기본 정책

| 항목 | 결정 내용 |
| --- | --- |
| HTTP Method | `DELETE` |
| Endpoint | `/api/v1/users/me` |
| 인증 | Access Token 필수 |
| 본인 확인 | 현재 비밀번호 재확인 |
| 사용자 데이터 | 하드 삭제 |
| 업로드한 X-ray 데이터 | 하드 삭제 |
| 성공 응답 | `204 No Content` |

### 6.2 처리 절차

1. `get_current_user()`를 통해 현재 사용자를 확인한다.
2. 요청으로 전달된 현재 비밀번호와 DB의 해시 비밀번호를 비교한다.
3. 비밀번호가 일치하지 않으면 `400 Bad Request`를 반환한다.
4. 현재 사용자를 삭제한다.
5. 외래키의 `ON DELETE CASCADE`에 의해 해당 사용자가 업로드한 `xray_images` 행을 자동 삭제한다.
6. 하나의 트랜잭션으로 모든 변경을 커밋한다.
7. 성공 시 응답 본문 없이 `204 No Content`를 반환한다.
8. 삭제 과정에서 오류가 발생하면 전체 트랜잭션을 롤백한다.

### 6.3 트랜잭션 원칙

사용자만 삭제되고 X-ray 데이터가 남거나, X-ray 데이터만 삭제되고 사용자가 남는 부분 성공 상태가 발생하지 않아야 한다. 사용자와 관련 X-ray 삭제는 동일 트랜잭션에서 원자적으로 처리한다.

## 7. 데이터베이스 변경 설계

### 7.1 변경 대상

`xray_images.uploader_id`가 `users.id`를 참조하는 외래키에 `ON DELETE CASCADE`를 적용한다.

변경 의도는 다음과 같다.

```python
uploader_id: Mapped[int] = mapped_column(
    Integer,
    ForeignKey("users.id", ondelete="CASCADE"),
    nullable=False,
)
```

### 7.2 마이그레이션

모델 변경은 Alembic 마이그레이션으로 실제 Database 스키마에 반영한다. 마이그레이션 파일에는 기존 외래키 제거와 `ON DELETE CASCADE`가 포함된 외래키 생성 작업이 포함되어야 한다.

SQLite에서는 외래키 변경 시 테이블 재생성이 필요할 수 있으므로 자동 생성된 마이그레이션을 그대로 적용하지 않고 `upgrade()`와 `downgrade()`를 검토한다.

### 7.3 삭제 영향 범위

사용자 삭제로 자동 삭제되는 범위는 해당 사용자가 `uploader_id`로 연결된 `xray_images` 행이다. 환자, 진료 기록 및 AI 분석 결과는 사용자 삭제의 직접 대상에 포함하지 않는다.

## 8. 오류 처리 설계

| 상황 | HTTP 상태 코드 | 처리 내용 |
| --- | ---: | --- |
| 회원 탈퇴 성공 | `204 No Content` | 응답 본문 없음 |
| 비밀번호 불일치 | `400 Bad Request` | 현재 비밀번호가 일치하지 않음을 반환 |
| 토큰 누락·형식 오류 | `401 Unauthorized` | 인증 필요 오류 반환 |
| 토큰 만료·위조·손상 | `401 Unauthorized` | 유효하지 않은 인증 오류 반환 |
| 역할 권한 부족 | `403 Forbidden` | 접근 권한 부족 오류 반환 |
| 사용자 없음 | `404 Not Found` | 인증 정보에 해당하는 사용자가 없음을 반환 |
| DB 삭제 실패 | `500 Internal Server Error` | 트랜잭션 롤백 후 내부 오류 반환 |

구체적인 오류 응답 Body 형식과 오류 코드는 프로젝트 공통 오류 처리 규칙에 맞춰 API 명세서에서 확정한다. 내부 예외 메시지나 보안상 민감한 정보는 응답에 포함하지 않는다.

## 9. API 성능 검증 설계

### 9.1 성능 기준

`NFR-USER-003`의 “최대 3초 이내”를 다음과 같이 해석한다.

> 지정된 로컬 테스트 환경에서 각 사용자 API의 단일 요청은 서버 시작 시간을 제외하고 3.0초 미만에 완료되어야 한다.

### 9.2 측정 대상

사용자 요구사항 정의서에 포함된 다음 API를 대상으로 한다.

- 회원가입
- 로그인
- 토큰 재발급
- 로그아웃
- 회원 목록 조회
- 회원 권한 변경
- 마이페이지 조회
- 회원 정보 수정
- 비밀번호 변경
- 회원 탈퇴

### 9.3 측정 방법

- API 테스트 클라이언트의 요청 시작 직전과 응답 수신 직후 시간을 측정한다.
- 각 성공 시나리오의 경과 시간이 `3.0초 미만`인지 검증한다.
- 테스트 전에 필요한 사용자 및 인증 데이터를 준비한다.
- 애플리케이션 시작 시간과 최초 의존성 설치 시간은 측정에서 제외한다.
- 각 테스트 결과에 엔드포인트, HTTP 상태 코드 및 응답시간을 기록한다.

본 단계는 요구사항 충족 여부를 확인하는 응답시간 테스트이며, 대규모 동시 요청에 대한 부하 테스트는 포함하지 않는다.

## 10. 테스트 설계

### 10.1 공통 인증

- 정상 Access Token으로 현재 사용자 조회 성공
- Authorization 헤더 누락 시 `401`
- Bearer 형식 오류 시 `401`
- 만료 토큰 사용 시 `401`
- 위조·손상된 토큰 사용 시 `401`
- Payload에 `user_id`가 없을 때 `401`
- 토큰의 사용자와 일치하는 DB 사용자가 없을 때 `404`
- 비활성 사용자 접근 차단

### 10.2 역할 기반 인가

- 허용된 역할의 접근 성공
- 허용되지 않은 역할의 접근 시 `403`
- 인증되지 않은 사용자는 역할 검사 전에 `401`

### 10.3 회원 탈퇴

- 정상 비밀번호로 회원 탈퇴 성공 및 `204` 반환
- 비밀번호 불일치 시 `400` 반환 및 데이터 유지
- 회원 삭제 후 해당 사용자 조회 불가 확인
- 회원 삭제 후 해당 사용자가 업로드한 `xray_images` 삭제 확인
- 다른 사용자가 업로드한 `xray_images` 유지 확인
- DB 처리 실패 시 사용자와 X-ray 데이터 모두 롤백되는지 확인
- 삭제된 사용자의 기존 Access Token으로 접근할 수 없는지 확인

### 10.4 성능

- 각 사용자 API의 정상 요청이 3.0초 미만인지 확인
- 성능 기준을 초과하면 측정값과 대상 API를 테스트 결과에 표시

## 11. 구현 전 확인 사항

- 비밀번호 검증 공통 함수의 위치와 사용법 확인

- 성능 테스트 실행 환경과 결과 기록 형식 확정
