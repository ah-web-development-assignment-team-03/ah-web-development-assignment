# 1. Event-Driven Architecture란?

Event-Driven Architecture(EDA)는

> **"어떤 이벤트(Event)가 발생하면 그 이벤트를 필요로 하는 시스템들이 이를 받아 각각의 작업을 수행하는 구조"** 입니다.

즉,

기존처럼

```
Client
 ↓
Server
 ↓
Database
```

처럼 하나의 요청이 하나의 응답을 만드는 것이 아니라,

```
회원가입 발생
        │
        ▼
회원가입 이벤트 생성
        │
 ┌──────┼─────────┐
 ▼      ▼         ▼
이메일   포인트    로그 저장
발송     지급
```

처럼

**이벤트 하나를 여러 서비스가 동시에 처리**합니다.

---

# Event란?

Event는

> "시스템에서 발생한 의미 있는 사건"

입니다.

예시

- UserCreated
- OrderCreated
- PaymentCompleted
- CommentAdded
- ImageUploaded
- NotificationCreated

즉,

```
회원가입했다.

↓

UserCreated Event
```

이 하나의 Event입니다.

---

# Event와 API의 차이

API는

```
A가 B를 호출한다.
```

EDA는

```
A가 Event만 발생시킨다.

누가 사용할지는 모른다.
```

즉

API는

```
A → B
```

처럼 강하게 연결되어 있고

EDA는

```
A

↓

Event

↓

B
C
D
E
```

처럼 느슨하게 연결됩니다.

이를

> Loose Coupling

이라고 합니다.

예를 들어 회원가입을 생각해보겠습니다.

회원가입 시

해야 할 일은

- Slack 알림
- 관리자 로그
- 추천인 포인트 지급
- 쿠폰 지급
- 문자 발송

기존 방식

```

↓

DB 저장

↓

이메일

↓

포인트

↓

로그

↓

쿠폰

↓

응답
```

모든 작업이 끝나야 응답됩니다.

사용자는

3~5초를 기다릴 수도 있습니다.

```
회원가입

↓

```

끝입니다.

```

```

# 4. EDA의 핵심 개념

EDA는 크게 4가지 요소로 구성됩니다.

```
Producer

↓

Broker

↓

Consumer

↓

Handler
```

---

## Producer

이벤트를 발생시키는 주체

예

```
회원가입 API
```

```
POST /signup
```

회원가입 성공

↓

UserCreated Event 발생

---

## Event Broker

이벤트를 전달하는 역할

대표적인 Broker

- Redis
- Kafka
- RabbitMQ
- AWS SQS
- Google Pub/Sub

이번 문서에서는 Redis를 사용합니다.

---

## Consumer

이벤트를 구독하는 프로그램입니다.

예

```
Email Service
```

```
UserCreated
```

이벤트를 기다립니다.

---

## Handler

실제 작업을 수행합니다.

예

```
이메일 발송

↓

SMTP 호출
```

# 6. Pub/Sub와 Message Queue 차이

## Pub/Sub

Publisher

↓

Topic

↓

모든 Subscriber에게 전달

```
          UserCreated

             │

     ┌───────┼────────┐

     ▼       ▼        ▼

 Email    Slack    Logging
```

특징

- 모든 구독자가 받음
- 저장되지 않음
- 실시간

---

## Message Queue

```
Task

↓

Queue

↓

Worker 하나가 가져감
```

```
Task1

↓

Queue

↓

Worker1
```

Task2

↓

Queue

↓

Worker2

특징

- 하나의 Consumer만 처리
- 작업 분산
- 재시도 가능

---

Redis Pub/Sub는

실시간 알림

Redis Streams는

Queue처럼 사용할 수 있습니다.

# 7. Redis란?

Redis는

Remote Dictionary Server

메모리 기반 NoSQL 데이터베이스입니다.

특징

- 매우 빠름
- In-Memory
- Key-Value
- Cache
- Pub/Sub
- Stream
- Queue
- Lock

등을 제공합니다.

---

Redis를 사용하는 이유

FastAPI에서

```
Event Broker
```

역할을 맡기 위해 사용합니다.

```
Channel

↓

```

```

```

채널

```

↓

signup

↓

subscribe
```

Subscriber는

계속

```

```

채널을 듣고 있습니다.

---

장점

- 빠름
- 구현 쉬움

단점

- 메시지가 저장되지 않음
- Consumer가 죽어 있으면 못 받음

# 9. Redis Streams

Streams는

Pub/Sub보다 발전된 형태입니다.

```
Producer

↓

Stream

↓

Consumer Group

↓

Worker
```

장점

- 저장됨
- ACK 가능
- 재시도 가능
- Consumer Group 지원

실무에서는

Pub/Sub보다 Streams를 더 많이 사용합니다.

# 16. 장점과 단점

## 장점

### 높은 확장성

Consumer만 추가하면 기능을 쉽게 확장할 수 있습니다.

### 빠른 응답

사용자는 이벤트 발행 후 즉시 응답을 받을 수 있습니다.

### 느슨한 결합(Loose Coupling)

Producer는 Consumer의 존재를 알 필요가 없습니다.

### 장애 격리

하나의 Consumer가 실패해도 다른 Consumer는 계속 동작할 수 있습니다.

### 유지보수 용이

기능별로 Consumer를 분리하여 관리할 수 있습니다.

---

## 단점

### 구조가 복잡해질 수 있음

이벤트 흐름을 이해하기 어려울 수 있습니다.

### 디버깅이 어려움

이벤트가 여러 Consumer를 거치므로 추적이 쉽지 않습니다.

### 메시지 유실 가능성

Redis Pub/Sub는 Consumer가 연결되어 있지 않으면 메시지를 받을 수 없습니다.

### 이벤트 중복 처리

네트워크 문제나 재시도로 인해 같은 이벤트가 여러 번 전달될 수 있으므로 **멱등성(Idempotency)** 을 고려해야 합니다.

---

# 17. 언제 사용하면 좋은가?

EDA가 적합한 경우

- 회원가입 후 여러 작업이 필요한 경우
- 주문 처리
- 결제 시스템
- 알림 시스템
- 로그 수집
- AI 추론 요청
- 이미지 처리
- 대용량 트래픽 서비스

EDA가 적합하지 않은 경우

- 단순 CRUD API
- 소규모 프로젝트
- 이벤트가 거의 발생하지 않는 시스템
- 실시간 응답보다 즉시 결과 반환이 중요한 업무

# 18. FastAPI + Redis EDA 설계 시 고려사항

## 1. Event Naming

명확한 이벤트 이름을 사용합니다.

예시

- UserCreated
- OrderPaid
- PaymentCompleted
- NotificationSent

---

## 2. Event Payload

이벤트에는 필요한 최소한의 데이터만 포함합니다.

예시

```json
{
  "event": "UserCreated",
  "user_id": 100,
  "email": "user@example.com",
  "created_at": "2026-07-24T15:30:00Z"
}
```

---

## 3. 멱등성(Idempotency)

Consumer가 같은 이벤트를 여러 번 받아도 동일한 결과가 나오도록 설계해야 합니다.

예시

- 이미 발송한 이메일은 다시 보내지 않음
- 이미 지급한 포인트는 중복 지급하지 않음

---

## 4. 재시도(Retry)

일시적인 오류가 발생하면 자동으로 재시도할 수 있도록 설계합니다.

---

## 5. Dead Letter Queue(DLQ)

여러 번 재시도해도 실패한 이벤트는 별도의 저장소(DLQ)에 보관하여 운영자가 확인할 수 있도록 합니다.

---

## 6. 모니터링

다음과 같은 항목을 지속적으로 모니터링합니다.

- 이벤트 발생 수
- 처리 성공/실패 수
- Consumer 지연 시간
- Queue 길이
- Redis 메모리 사용량

---

# 19. 정리

FastAPI와 Redis를 이용한 Event-Driven Architecture는 **API 서버와 후속 작업을 분리하여 응답 속도와 확장성을 크게 향상시키는 아키텍처**입니다.

핵심은 다음과 같습니다.

1. **Producer(FastAPI)** 는 이벤트만 발행합니다.
2. **Redis** 는 이벤트를 전달하는 Broker 역할을 합니다.
3. **Consumer** 는 필요한 이벤트를 구독하여 독립적으로 처리합니다.
4. **Pub/Sub** 는 실시간 이벤트 전달에 적합하지만 메시지를 저장하지 않습니다.
5. **Redis Streams** 는 메시지 저장, ACK, Consumer Group 등을 지원하여 실무에서 더욱 안정적인 이벤트 처리에 적합합니다.
6. EDA를 도입하면 시스템 간 결합도를 낮추고(Loose Coupling), 기능 확장과 유지보수를 쉽게 할 수 있습니다.
7. 실무에서는 멱등성, 재시도, Dead Letter Queue(DLQ), 모니터링 등을 함께 고려해야 안정적인 운영이 가능합니다.
