# 1. EDA란?

**"이벤트가 발생하면 이를 필요로 하는 시스템들이 받아 각각의 작업을 수행하는 구조"**

기존 방식(Request-Response)과 달리, 이벤트 하나를 여러 서비스가 동시에 처리합니다.

- API: `A → B` (강한 결합)
- EDA: `A → Event → B, C, D` (느슨한 결합, Loose Coupling)

---

# 2. 왜 사용하는가?

회원가입 시 기존 방식은 `DB 저장 → 이메일 → 포인트 → 로그 → 응답` 순으로 모든 작업이 끝나야 응답됩니다.

EDA에서는 `DB 저장 → Event 발행 → 응답`, 나머지(이메일·포인트·로그)는 각 Consumer가 독립적으로 처리합니다.

→ **응답 속도 향상 + 기능 분리 + 확장 용이**

---

# 3. 핵심 구성요소

| 요소 | 역할 |
|------|------|
| Producer | 이벤트를 발생시키는 주체 (FastAPI) |
| Broker | 이벤트를 전달 (Redis) |
| Consumer | 이벤트를 구독하여 처리 |
| Handler | 실제 비즈니스 로직 수행 |

---

# 4. Redis Pub/Sub vs Streams

|  | Pub/Sub | Streams |
|--|---------|---------|
| 메시지 저장 | X | O |
| ACK / 재시도 | X | O |
| Consumer Group | X | O |
| 적합 용도 | 실시간 알림 | 실무 이벤트 처리 |

→ 실무에서는 **Streams**를 더 많이 사용합니다.

# 6. 장점과 단점

**장점**

- 빠른 응답 (이벤트 발행 후 즉시 응답)
- 높은 확장성 (Consumer 추가만으로 기능 확장)
- Loose Coupling (Producer는 Consumer를 알 필요 없음)
- 장애 격리 (하나의 Consumer 실패가 전체에 영향 없음)

**단점**

- 구조 복잡도 증가
- 디버깅 어려움 (이벤트 흐름 추적 난이도)
- 메시지 유실 가능성 (Pub/Sub)
- 이벤트 중복 처리 → 멱등성 설계 필요

---

# 7. 언제 사용하면 좋은가?

**적합**: 회원가입, 주문/결제 처리, 알림 시스템, 대용량 트래픽

**부적합**: 단순 CRUD, 소규모 프로젝트, 즉시 결과 반환이 필요한 업무

---

# 8. 설계 시 고려사항

1. **Event Naming** — 명확한 이름 사용 (`UserCreated`, `OrderPaid`)
2. **멱등성(Idempotency)** — 같은 이벤트를 여러 번 받아도 동일한 결과
3. **재시도(Retry)** — 일시적 오류 시 자동 재시도
4. **Dead Letter Queue(DLQ)** — 반복 실패 이벤트 별도 보관
5. **모니터링** — 이벤트 수, 처리 성공/실패, Queue 길이

---

# 9. 정리

FastAPI + Redis EDA는 **API와 후속 작업을 분리하여 응답 속도와 확장성을 향상**시키는 아키텍처입니다.

- **Producer(FastAPI)** → 이벤트만 발행
- **Redis** → Broker 역할
- **Consumer** → 독립적으로 이벤트 처리
- 실무에서는 **Redis Streams** + 멱등성 + DLQ 설계 필수
