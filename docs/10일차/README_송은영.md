# Stage 4 - 프로젝트 과정 총 정리
이 문서는 프로젝트 진행 과정을 Team Rule 정의부터 QA까지 10단계로 나눠 팀이 실제로 어떻게 작업해왔는지 되돌아본 기록입니다.

## 1. Team Rule 정의

프로젝트 시작 전 코어타임(평일 15:20~16:00)과 회의 방식, Git 브랜치/커밋/PR/코드리뷰 규칙, 충돌 해결 원칙, 업무 기록 방식까지 팀 협업 규칙을 먼저 정하고 시작했습니다.

"모든 변경은 별도 브랜치를 만들어 PR을 통해서만 `develop`에 병합"이라는 원칙을 처음부터 세워, 이후 모든 작업의 기준이 됐습니다.

---

## 2. 사용자 요구사항 정의

운영진이 매일 REQ-ID 형식(기능/비기능 구분, Recall·API 응답시간 같은 정량 기준 포함)으로 요구사항 정의서를 제공했고 팀은 이를 읽고 해석해 API 명세로 옮기는 역할을 했습니다.

예를 들어 6일차 AI 폐렴 예측 사용자 요구사항 정의서에는 `REQ-PRED-001`/`002`(기능)와 `NFR-PRED-001`/`002`(Recall≥0.90, API 3초 이내)가 함께 제시돼 구현 전에 성능 기준까지 미리 확인하고 시작할 수 있었습니다.

다만 요구사항을 직접 작성해본 경험은 아직 없어 다음 파이널 프로젝트부터는 팀이 직접 요구사항을 정의하는 과정이 필요합니다.

---

## 3. API 명세서 작성

받은 요구사항을 바탕으로 기능별 담당자가 구현에 앞서 API 명세서(엔드포인트, 요청/응답 스키마, 권한, 에러 코드)를 먼저 작성하고 PR로 올려 팀 리뷰를 거쳤습니다.

같은 리소스를 다루는 명세끼리는 서로 맞춰나갔는데 예를 들어 `REQ-PRED-001`(예측 실행)과 `REQ-PRED-002`(결과 조회) 명세는 각자 초안을 쓴 뒤 리뷰에서 응답 필드명·타입·에러 형식을 통일하고 `(record_id, ai_model)` UNIQUE 제약이나 `heatmap_url` nullable 여부 같은 DB 설계 이슈까지 미리 합의한 뒤 구현으로 넘어갔습니다.

---

## 4. Git & GitHub Branch 전략 구성

1일차 팀 룰 정의 때 `develop`을 기준으로 하는 Git Flow 브랜치 전략까지 함께 결정했습니다.

```text
main       ─ 배포 가능한 안정 버전만 유지
develop    ─ 실제 작업이 모이는 통합 브랜치
feat/*, fix/*, docs/*, release/*, hotfix/*  ─ develop에서 분기해 작업 후 PR로 병합
```

같은 파일명(predictions.py, pages.js 등)으로 서로 다른 사람이 서로 다른 부분(함수)을 작성하면서 병합 충돌이 여러 번 발생했는데 그때마다 양쪽이 작성한 로직을 온전히 살려 함수 단위로 합치는 방식으로 해결했습니다.

---

## 5. 프로젝트 세팅

3일차에 제공된 템플릿 구조(`apis/`, `core/`, `models/`, `repositories/`, `schemas/`, `services/`로 이미 계층이 나뉜 스켈레톤)를 함께 뜯어보며 각 폴더의 역할과 DB 연결·SQLAlchemy 모델·Alembic 마이그레이션 흐름을 정리했습니다.

이 구조를 그대로 레이어드 아키텍처로 채택해, 이후 모든 기능을 같은 패턴으로 구현했습니다.

```text
API → Service → Repository → Model → DB
```

---

## 6. API 및 AI 워커 코드 작성 후 Branch 전략을 통한 코드 병합

```text
회원가입/인증 → 환자 관리 → 진료기록 → AI 폐렴 예측
```

각 기능마다 아래 순서를 지켰습니다.

```text
명세서 작성 → 리뷰 → 구현 → PR → 팀원 3명 리뷰 승인 → develop 병합
```

AI 모델(`worker/model.py`, 5-fold 앙상블 추론)은 API 코드와 별도 브랜치에서 병렬로 개발된 뒤 예측 실행 API가 `predict()` 함수를 호출하는 방식으로 통합됐습니다.

`REQ-PRED-001`(예측 실행)과 `REQ-PRED-002`(결과 조회)처럼 같은 파일을 여러 명이 나눠 작업한 경우 먼저 머지되는 쪽을 기준으로 나머지가 `develop`과의 충돌을 직접 해결하며 병합하는 방식으로 조율했습니다.

## 7. 아키텍처 설계 및 적용

9일차에 AI 추론처럼 오래 걸리는 작업을 FastAPI가 직접 처리할 때 생기는 문제(응답 지연, 서버 자원 점유, 요청 폭주 시 장애, 중복 처리)를 팀원 각자 정리하고 공유했습니다.

이를 해결하기 위해 FastAPI(Producer)와 AI Worker(Consumer)를 Redis(Message Broker)로 분리하는 Event-Driven Architecture를 설계 방향으로 정했습니다.

```text
Client → FastAPI (요청 검증·작업 등록) → Redis (작업 대기열) → AI Worker (추론 실행) → DB (결과 저장)
```

FastAPI는 요청 검증과 작업 등록·상태 조회만 담당하고, 실제 AI 연산은 별도 Worker 프로세스가 Redis 큐에서 가져와 처리하도록 역할을 나눴으며 동시 요청으로 인한 중복 실행·결과 덮어쓰기를 막기 위한 멱등성(`task_id`/`Idempotency-Key` 기반 중복 차단)과 ACK 시점, 재시도 정책까지 함께 정리했습니다.

## 8. 도커 인프라 관련 파일 작성

8일차에 Dockerfile과 docker-compose.yml을 작성해 FastAPI 앱과 MySQL을 컨테이너로 띄우고 docker compose up --build로 두 컨테이너가 모두 healthy 상태로 뜨는 것까지 확인했습니다.

도커 부분은 팀원 각자 PR을 올린 뒤 4번처럼 로직을 합치는 대신 채택된 코드를 머지 나머지 PR은 닫는 방식으로 정리했습니다. 이후 Redis와 AI Worker 컨테이너를 추가해 7번(Event-Driven Architecture)에서 설계한 구조를 실제로 컨테이너 단위로 분리했고 리팩토링 과정에서 컨테이너 기동 시 alembic upgrade head를 자동 실행하도록 하고 MySQL로 완전히 전환하면서 더 이상 필요 없어진 SQLite 호환 코드를 정리했습니다.

## 10. QA 진행

7일차에 제공된 프론트엔드 템플릿을 실제 API에 연결하며 화면 단위(로그인, 환자 관리, 진료기록, AI 예측 등)로 직접 테스트했습니다. 브라우저 네트워크 탭으로 실제 요청·응답을 하나씩 확인하며 원인을 찾아 수정했습니다.

| 발견한 불일치 | 내용 |
| --- | --- |
| 엔드포인트 경로 | `/predict` vs `/predictions` |
| 응답 구조 | 배열 vs `{items}` |
| 필드명 | `phone_number` vs `phone` |
| enum 값 | `male` vs `M` |
| 백엔드 누락 | `xray_image_url` 항상 null, 상세 응답의 `patient_id` 누락 |

이 과정에서 발견한 문제들을 함께 고쳤고 결과를 `docs/7일차_앱_실행화면.md`에 화면 캡처와 함께 정리했습니다.
